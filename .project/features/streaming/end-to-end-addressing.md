# End-to-End TX Addressing: Deep Analysis

## The Question

Should the actor system use the **same addresses** from frontend component to backend actor instance and back? What does that mean concretely, what does it buy us, what does it cost, and what happens when hundreds of frontends connect simultaneously?

---

## The Two Address Spaces Today

### Frontend Address Space (Browser)

Every browser tab runs its own Matrix with a flat `children` map:

```
matrix.children = {
  // Classes (registered by Actor.subclass())
  "Component":   Component,
  "NTT":         NTT,
  "Product":     Product DynamicClass,
  "Comment":     Comment DynamicClass,

  // Component instances (registered in Component constructor)
  "NTTList-k7f3x2m1l":    <ntx-list model="Product">,
  "NTTStream-9p2qt4r1m":  <ntx-stream model="Product" method="ask">,
  "NTTItem-abc123def456":  <ntx-item>,
  ...
}
```

**Address format**: `{ClassName}-{random}` (e.g., `NTTStream-k7f3x2m1labcdef`)
**Generated by**: `Component.js:78` — `this.constructor.name + '-' + generateId()`
**Uniqueness**: Per-tab (Math.random + Date.now → practically unique)
**Lifecycle**: Created in constructor, **never deregistered** (no cleanup in `disconnectedCallback`)

Entity instances live inside their DynamicClass's `instances` map, not directly in the Matrix:
```
Product.instances = { "1": <Product#1>, "42": <Product#42> }
```

Routing: Matrix checks first segment of target. `"Product"` → Product class → class routes to instance. `"NTTStream-abc123"` → component instance directly.

### Backend Address Space (Server)

One Matrix, shared across all connections:

```python
matrix._children = {
  'products':  Product,     # ActorModel class (from __tablename__)
  'users':     User,        # ActorModel class
  'api':       NetworkAPI,  # adapter instance (addr='api')
  'ws':        NetworkWS,   # adapter instance (addr='ws')
}
```

**Address format**: `__tablename__` (e.g., `'products'`)
**Generated by**: `ActorMeta.__new__` in `actor.py:83`
**Uniqueness**: Globally unique (one class per tablename)
**Lifecycle**: Created at class definition time, permanent

Entity instances do NOT have their own addresses. `Product.get(42)` returns an instance whose `_addr` equals the class `__addr__` (`'products'`). The entity ID travels in `tx.data['id']`, not in the address.

Routing: Matrix checks first segment. `'products'` → Product class → `handler_crud()` or `handler()` resolves by name + data.

### The Boundary: Two Translation Patterns

**WS adapter** — translates at the boundary, preserves frontend identity in meta:
```
Frontend: {source: 'NTTStream-abc', target: 'http://localhost:5000/products/42', name: 'ASK'}
    ↓ _translate_incoming()
Backend:  TX(source='ws', target='products', name='ask', meta={ws_source: 'NTTStream-abc', ws_target: 'http://...', ws_name: 'ASK'})
    ↓ Actor system processes, reply goes back to target='ws'
    ↓ _translate_outgoing() reconstructs frontend addresses from meta
Frontend: {source: 'http://localhost:5000/products/42', target: 'NTTStream-abc', name: 'ASK'}
```

**HTTP adapter** — no translation for streaming (the bug):
```
Frontend: NetworkAdapter builds TX from closure vars
Backend:  TX(source='api', target='products', name='ask', meta={stream: true})
    ↓ Actor system processes, chunks go back to target='api'
    ↓ _sse_from_stream() serializes full TX envelope (backend addresses)
Frontend: receives {source: 'products/products', target: 'api'} — meaningless to frontend routing
```

## What "Same Addresses End-to-End" Could Mean

There are three levels of address unification, each progressively deeper:

### Level 1: Meta Preservation (Option C from the previous doc)

Frontend addresses ride in TX meta through the backend. Backend routing uses its own addresses internally. The transport adapter reconstructs frontend addresses on response.

```
Frontend source: "NTTStream-abc123"      → meta.frontend_source
Backend source:  "api"                   → TX.source (for routing)
Response:        target = meta.frontend_source = "NTTStream-abc123"
```

**This is what the WS adapter already does.** The addresses aren't "the same" — they're preserved and reconstructed. Two address spaces, bridged by meta.

### Level 2: Transparent Proxy

The backend uses frontend addresses directly in TX routing. `NTTStream-abc123` becomes a real routable target in the backend Matrix. The transport adapter registers a virtual actor for each connected frontend component.

```
Frontend sends: TX(source='NTTStream-abc123', target='products/42', name='ask')
Backend Matrix has: {'products': Product, 'api': API, 'NTTStream-abc123': <VirtualActor>}
Backend routes reply: TX(target='NTTStream-abc123') → VirtualActor → sends over WS/SSE
```

**This is genuinely unified addressing.** One namespace, one routing table, frontend actors are first-class citizens in the backend.

### Level 3: Distributed Actor System

Frontend and backend share a single logical Matrix. Components and models are peers. Any actor can address any other actor, regardless of which side of the network it lives on. Location transparency — you don't know (or care) whether the target is local or remote.

```
NTTStream-abc123.send(TX(target='products/42', name='ask'))
  → local Matrix doesn't have 'products' → routes to network adapter
  → arrives at backend Matrix → routes to Product class → handler
  → reply TX(target='NTTStream-abc123')
  → backend Matrix doesn't have 'NTTStream-abc123' → routes to network adapter
  → arrives at frontend Matrix → routes to NTTStream component
```

**This is the actor model's original promise.** Erlang/OTP, Akka, Orleans all work this way.

## Analysis by Level

### Level 1: Meta Preservation

This is Option C from the previous document. Already analyzed. The key properties:
- Backend address space unchanged
- Frontend addresses pass through as opaque strings
- No coupling between frontend class names and backend routing
- Backend can log/observe frontend identity without depending on it
- **Scale**: No impact. Meta is per-request, carried in the TX, garbage-collected with the request.

### Level 2: Transparent Proxy — The Interesting Middle Ground

#### What Changes

The backend Matrix would need a **virtual actor registry** for connected frontends:

```python
# On WS connect or SSE stream start:
class VirtualFrontendActor:
    """Proxy that routes TX messages back to a specific frontend component."""
    def __init__(self, addr, transport, connection):
        self.addr = addr              # 'NTTStream-abc123'
        self.transport = transport     # 'ws' or 'sse'
        self.connection = connection   # WebSocket object or SSE response generator

    async def inbox(self, tx):
        if self.transport == 'ws':
            await self.connection.send_json(tx.to_dict())
        elif self.transport == 'sse':
            await self.connection.put(tx)  # feed SSE queue

# Registration:
matrix.register(VirtualFrontendActor('NTTStream-abc123', 'ws', ws_connection))
```

Backend routing becomes:
```python
# Matrix.inbox():
target_root = tx.target.split('/')[0]
if target_root in self._children:
    await self._children[target_root].inbox(tx)
# 'NTTStream-abc123' → VirtualFrontendActor → sends to browser
```

#### Coupling Introduced

| What | Coupling | Consequence |
|------|----------|-------------|
| Frontend address format | Backend must parse `{ClassName}-{hash}` to find the right transport | If frontend changes address generation (e.g., shorter hashes), backend doesn't care — it's opaque |
| Address namespace collision | Frontend `NTTStream-abc` must not collide with backend `products` | Mitigated: frontend addresses always contain `-` (hyphenated), backend uses bare tablenames |
| Registration lifetime | Backend must know when to register/deregister virtual actors | WS: register on connect, deregister on disconnect. SSE: register on stream start, deregister on stream end |
| Matrix size | Backend Matrix children dict grows with connected frontends | 100 browsers × 50 components = 5,000 entries (if all registered) |

The coupling is **structural, not semantic**. The backend doesn't need to know what `NTTStream` does — it just routes messages to it. The address is an opaque string. This is the same kind of coupling a mail server has with email addresses: it routes by address without understanding what's behind it.

#### What This Enables

1. **Backend-initiated messages to specific components.** An agent processing a long task can send progress updates directly to the component that requested it:
   ```python
   await matrix.send(TX(
       source='products/42',
       target='NTTStream-abc123',  # specific component
       name='PROGRESS',
       data={'percent': 45, 'message': 'Analyzing...'}
   ))
   ```

2. **Cross-component coordination through backend.** Component A can tell the backend to notify Component B:
   ```python
   # Agent decides: "I should update the product list too"
   await matrix.send(TX(
       source='products/42',
       target='NTTList-def456',  # different component in same browser
       name='REFRESH',
       data={}
   ))
   ```

3. **Backend observability with routing context.** Logs show:
   ```
   [Matrix] Routing 'ask' from NTTStream-abc123 to products
   [Matrix] Streaming 3 chunks from products to NTTStream-abc123
   ```

4. **Multi-modal output.** An agent stream can target different components per chunk:
   ```python
   yield TX(target='NTTStream-abc123', data={'text': 'Here is the analysis...'})
   yield TX(target='NTTChart-xyz789', data={'chart': {...}})
   ```

#### What This Costs

1. **Virtual actor lifecycle management.** Every SSE stream or WS connection must register/deregister virtual actors. For SSE (stateless HTTP), this means:
   - Register on stream start
   - Deregister on stream end, client disconnect, or timeout
   - Need heartbeat or keepalive to detect dead SSE connections
   - The `finally` block in `stream()` must clean up the virtual actor

2. **Matrix bloat under load.** The backend Matrix children dict becomes proportional to connected components, not just registered models:
   ```
   Before: {'products': Product, 'users': User, 'api': API, 'ws': WS}  → 4 entries
   After:  + 5000 virtual frontend actors  → 5004 entries
   ```
   Dict lookup is O(1), so routing isn't slower. But iteration (e.g., `matrix._children.items()`) becomes expensive. Any code that enumerates children hits 5000+ entries.

3. **Address collision across browsers.** Two browsers could theoretically generate the same address (`NTTStream-abc123`). Frontend uses `Math.random().toString(36) + Date.now().toString(36)` — collision probability is negligible for a single browser but increases with concurrent sessions. Mitigation: prefix with connection/session ID, or use UUIDs.

4. **Stale actor cleanup.** If a browser tab crashes without clean disconnect:
   - WS: disconnect event fires, cleanup runs
   - SSE: no disconnect event. The `StreamingResponse` stops being pulled, but the virtual actor persists until the stream's `finally` block runs. Non-streaming SSE has no cleanup trigger at all.
   - Need a TTL/reaper for virtual actors: "if no message received in 60s, deregister"

5. **Security surface.** A malicious frontend could register an address that shadows a real backend actor:
   - Frontend sends: `source: 'products'` (pretending to be the Product class)
   - Backend registers a virtual actor at `'products'` → shadows the real model
   - Mitigation: namespace enforcement. Frontend addresses must match `/{Component}-{hash}/` pattern. Reject registration of bare tablenames.

### Level 3: Distributed Actor System — The Full Vision

#### What This Would Require

1. **Location-transparent routing.** Matrix.inbox() doesn't distinguish local vs remote actors. If the target isn't in local children, it queries a distributed registry or broadcasts to peer nodes.

2. **Distributed actor registry.** Not just backend knows about frontend — frontend also knows about backend actors as virtual targets. `products` is a virtual actor in the frontend Matrix that routes to the network.

3. **Bidirectional discovery.** Backend tells frontend "I have these actors" and frontend tells backend "I have these actors." Schema fetch is a special case of this.

4. **Consistent addressing.** Both sides use the same format. No URL-based targets on the frontend, no tablename-based targets on the backend. One address space.

#### Why This Is Overkill (For Now)

The frontend and backend have **fundamentally different actor lifecycles**:

| Property | Frontend actors | Backend actors |
|----------|----------------|----------------|
| Created by | DOM (user navigates, components mount) | Class definition (server starts, models load) |
| Destroyed by | DOM removal (navigate away, close tab) | Never (classes persist for server lifetime) |
| Instance count | 10-100 per browser tab, ephemeral | 4-10 per server, permanent |
| State | In-memory, per-tab, lost on refresh | In database, shared, persistent |
| Identity | Random per session (`NTTList-k7f3x2m1l`) | Deterministic per model (`products`) |
| Multiplicity | N copies across N browsers | One canonical instance |

A truly distributed actor system (Level 3) makes sense when actors on both sides have **similar lifecycles and multiplicity** — like microservices talking to each other, or Erlang nodes in a cluster. But frontend components are ephemeral UI bindings and backend models are persistent data managers. They're not peers — they're collaborators with very different roles.

Level 2 (transparent proxy) gives you the useful parts of distributed addressing (backend can target specific components) without pretending that `<ntx-list>` and `Product` are the same kind of actor.

## What Happens with Hundreds of Concurrent Frontends

### The Numbers

Assume: 200 concurrent browser tabs, each with ~30 active components (lists, items, streams, methods).

| Metric | Level 1 (Meta) | Level 2 (Virtual Actors) |
|--------|----------------|--------------------------|
| Backend Matrix children | 4-10 (models + adapters) | 4-10 + up to 6,000 virtual actors |
| Memory per virtual actor | N/A | ~200-500 bytes (addr + transport ref + connection ref) |
| Total virtual actor memory | 0 | ~1.2-3 MB |
| Dict lookup time | O(1) | O(1) (hash table, same cost) |
| Dict iteration cost | Negligible (4-10 items) | 6,000+ items (lifecycle broadcasts, debug dumps) |
| `_pending` entries (per adapter) | 1 per in-flight request/stream | Same — unchanged |

### Scale Concern 1: Do We Register All Components or Only Active Streams?

**Option A: Register everything.** Every component in every browser becomes a virtual actor. 200 browsers × 30 components = 6,000 entries. Most are idle (an `<ntx-list>` that already rendered doesn't need to be addressable from the backend). This is wasteful.

**Option B: Register on demand.** Only register a virtual actor when the backend needs to address a specific component — i.e., during streaming or server-push. An `<ntx-stream>` that starts an `ask` stream registers; the registration is removed when the stream ends. Most components never register.

With Option B, the realistic numbers:
- 200 browsers, maybe 10 concurrent streams = **10 virtual actors** at peak
- A burst of 50 users all asking questions simultaneously = **50 virtual actors** for ~30 seconds, then cleaned up
- Steady state: close to zero

**Option B is clearly the right choice.** Virtual actors are ephemeral, tied to active interactions, not passive UI state.

### Scale Concern 2: Address Collision

Frontend addresses are generated by `Math.random().toString(36).substring(2) + Date.now().toString(36)`:
- `Math.random()` → ~10 chars of base-36 ≈ 47 bits of entropy
- `Date.now()` → ~8 chars of base-36 (current epoch), changes every millisecond

With 6,000 concurrent addresses, birthday paradox collision probability: ~2^-34 per pair, negligible in practice. But if you're paranoid, prefix with a session token:

```
NTTStream-{session_id}-{random}
```

where `session_id` comes from the WS connection or JWT. This guarantees uniqueness across sessions.

### Scale Concern 3: Cleanup on Disconnect

**WebSocket**: Clean disconnect fires `WebSocketDisconnect`, triggering the `finally` block that removes the connection from `_connections`. All virtual actors for that connection should be cleaned up simultaneously. This requires a **reverse index**: `connection_id → [virtual_actor_addr, ...]`.

```python
# On disconnect:
for addr in self._connection_actors.pop(client_id, []):
    matrix.deregister(addr)
```

**SSE/HTTP**: No disconnect event. The `StreamingResponse` stops being consumed when the client disconnects. The `stream()` generator's `finally` block fires when FastAPI/Starlette detects the closed connection (usually on the next yield attempt). The virtual actor cleanup goes there:

```python
# In _sse_from_stream():
try:
    async for chunk in adapter.stream(tx, timeout=120.0):
        yield f"event: chunk\ndata: {json.dumps(translated)}\n\n"
finally:
    matrix.deregister(frontend_source_addr)  # cleanup virtual actor
```

**Edge case**: Browser tab crash with no clean close. WS eventually fires a TCP timeout (seconds to minutes depending on keepalive settings). SSE: the HTTP connection hangs until the server-side timeout (120s) fires. Virtual actor persists for up to 120 seconds after the tab dies.

Mitigation: **TTL reaper** — a periodic task (every 60s) that checks virtual actors' last-message timestamp and removes stale ones. This is cheap: iterate a small set of virtual actors (Option B keeps this set small).

### Scale Concern 4: One Backend Matrix, Many Frontend Matrices

This is the fundamental asymmetry. There is **one** backend actor system serving **N** frontend actor systems. Each frontend Matrix is isolated — Browser A's `NTTStream-abc` and Browser B's `NTTStream-def` are separate actors in separate Matrices.

The backend Matrix is the **convergence point**. It must distinguish between:
- `NTTStream-abc` (Browser A) and `NTTStream-def` (Browser B)
- Both targeting `products/42` with method `ask`
- Each must get their own response stream

With Level 1 (meta preservation), this is automatic — each HTTP request or WS message carries its own meta. No shared state.

With Level 2 (virtual actors), this works because addresses are unique per component instance. `NTTStream-abc` and `NTTStream-def` are different entries in `matrix._children`. Each gets their own response routing.

**The concern is not correctness (that works) but cognitive model.** A developer looking at the backend Matrix sees:
```python
matrix._children = {
    'products': Product,
    'users': User,
    'api': NetworkAPI,
    'ws': NetworkWS,
    'NTTStream-k7f3x2m1l': VirtualActor,  # Browser A, stream to product 42
    'NTTStream-9p2qt4r1m': VirtualActor,  # Browser B, stream to product 7
    'NTTStream-abc123def': VirtualActor,  # Browser C, stream to product 42
}
```

This mixing of permanent infrastructure actors (`products`, `api`) with ephemeral client-bound actors (`NTTStream-*`) in the same namespace could be confusing. Mitigation: separate namespace or prefix:

```python
matrix._children = {
    'products': Product,       # permanent
    'users': User,             # permanent
    'api': NetworkAPI,         # permanent
    'ws': NetworkWS,           # permanent
}
matrix._remotes = {            # separate dict
    'NTTStream-k7f3x2m1l': VirtualActor,
    'NTTStream-9p2qt4r1m': VirtualActor,
}
```

Routing checks `_children` first, then `_remotes`. Clear separation of concerns.

## The Coupling Spectrum

### What You're Coupling

| Level | Frontend → Backend coupling | Backend → Frontend coupling |
|-------|----------------------------|----------------------------|
| **Level 0** (current HTTP) | Frontend knows API URLs | Backend knows nothing about frontend |
| **Level 1** (meta preservation) | Frontend sends its address in meta/header | Backend reads meta for logging/routing, but doesn't depend on it |
| **Level 2** (virtual actors) | Frontend address becomes a routable entity in backend | Backend registers/deregisters virtual actors, routes to them |
| **Level 3** (distributed) | Both sides discover and route to each other | Full bidirectional dependency |

### What You're Gaining at Each Level

| Capability | L0 | L1 | L2 | L3 |
|------------|----|----|----|----|
| Bug fix (streaming display) | No | Yes | Yes | Yes |
| Backend observability | No | Yes | Yes | Yes |
| Backend-to-specific-component messaging | No | No | Yes | Yes |
| Agent multi-target streaming | No | No | Yes | Yes |
| Backend-initiated push to component | No | No | Yes | Yes |
| Location-transparent routing | No | No | No | Yes |
| Frontend-to-frontend via backend | No | No | Possible | Native |

### What You're Giving Up at Each Level

| Concern | L0 | L1 | L2 | L3 |
|---------|----|----|----|----|
| Backend simplicity | Full | Nearly full | Moderate complexity added | Significant complexity |
| Stateless HTTP model | Yes | Yes | Partially (virtual actor lifecycle) | No |
| Independent deploy | Full | Full | Backend must handle address protocol | Tight version coupling |
| Backend Matrix is small | Yes (4-10 entries) | Yes | Grows with active interactions | Grows with all connected components |
| No cleanup logic needed | Yes | Yes | Need reaper/cleanup | Need distributed GC |
| Security surface | Minimal | Minimal | Address spoofing possible | Full mutual trust required |

## Recommendation

### For the Streaming Bug Fix: Level 1 (Meta Preservation)

This is Option C from the previous doc. It fixes the bug, aligns HTTP with the WS adapter's existing pattern, gives backend observability, and adds zero coupling. **This should happen regardless of the deeper architectural decision.**

### For the Architecture: Level 2 with Lazy Registration

Level 2 unlocks the capabilities that matter for the agent-driven future (backend-to-component messaging, multi-target streaming, agent output routing) without the complexity of a full distributed actor system.

**But only with lazy registration** (Option B from the scale analysis): virtual actors are created only when an active interaction needs backend-to-frontend targeting (streaming, server push). Idle components are never registered. This keeps the backend Matrix small (typically <50 virtual actors even with hundreds of connected browsers) and limits cleanup complexity to active interactions.

### Implementation Path

1. **Now**: Level 1 (Option C) — fix the streaming bug with meta preservation. ~40 LOC, 3 files.
2. **When agents need to target components**: Level 2 with lazy registration. Build `VirtualActor` class, `_remotes` dict on Matrix, register/deregister in stream lifecycle. ~100 LOC, 3-4 files.
3. **Probably never**: Level 3. The frontend and backend actor lifecycles are too different to justify a fully distributed system. The cost/benefit ratio is poor for a web application.

### The Key Insight

The question isn't "should we use the same addresses" — it's "should the backend be able to address frontend components by name." Level 1 says "the backend carries the name but doesn't use it for routing." Level 2 says "the backend can route to it." Level 3 says "everyone can route to everyone."

Level 2 is the sweet spot: the backend gains the ability to target specific frontend components (critical for agent workflows) without pretending that ephemeral DOM elements and persistent database models are the same kind of actor. The asymmetry is real and should be reflected in the architecture — separate namespaces (`_children` vs `_remotes`), separate lifecycles (permanent vs session-bound), separate cleanup (never vs TTL reaper).

## Appendix: Address Format Reference

### Frontend
```
Component instance:  NTTStream-k7f3x2m1labcdef     (ClassName-randomHash)
DynamicClass:        Product                         (model name)
Entity instance:     42                              (DB id, within class scope)
Entity reference:    Product/42                      (hierarchical, for routing)
Remote target:       http://localhost:5000/products   (full URL, triggers network send)
```

### Backend
```
ActorModel class:    products                        (__tablename__)
Adapter instance:    api / ws / mcp                  (explicit addr in __init__)
Matrix:              matrix                          (hardcoded)
```

### WS Wire Format (already working)
```
Frontend → Backend:  {source: 'NTTStream-abc', target: 'http://localhost:5000/products/42', name: 'ASK'}
Backend TX:          TX(source='ws', target='products', meta={ws_source: 'NTTStream-abc', ...})
Backend → Frontend:  {source: 'http://localhost:5000/products/42', target: 'NTTStream-abc', name: 'ASK'}
```
