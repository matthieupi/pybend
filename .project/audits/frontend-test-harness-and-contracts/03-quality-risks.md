# Frontend Test Harness And Contracts — Quality Risks

## Scope

This report audits the frontend test harness and frontend contract tests around the reproduced command:

```bash
python3 scripts/run-frontend-tests.py
```

The focus is failure trustworthiness: whether failures indicate product regression, stale assertions, unresolved contract decisions, or harness/infrastructure fragility. Product and test source were treated as read-only; this report is the only written artifact.

## Executive Summary

The current frontend test failures are not a single product regression. They are a mixed state where some assertions are stale against the documented current frontend architecture, some harness configs still point at pre-split paths/env names, and a few runtime/component behaviors look like real product risks that should be pinned with narrower tests before broad fixes.

The default runner is useful because it keeps going after suite failures and writes an overview, but it currently aggregates five suites with different app roots, environment names, server startup patterns, and database marker schemes (`scripts/run-frontend-tests.py:85`, `scripts/run-frontend-tests.py:95`, `scripts/run-frontend-tests.py:109`, `scripts/run-frontend-tests.py:122`, `scripts/run-frontend-tests.py:135`). That makes broad red output hard to classify unless each cluster is triaged independently.

The clearest stale-test clusters are component expectation mismatches where tests assert older contracts: `Component.SIZES` as five modes while implementation and docs now include `row`, inline `<style>` for `ntx-ref-picker` while implementation links a stylesheet, and `.placeholder` in `ntx-profile` while implementation renders `.profile-note`. The clearest infrastructure clusters are import-level failures for example-local components being imported through the package alias, grants/perf Playwright configs pointing at old paths, and server startup relying on marker-file shell substitution.

The highest-risk product/runtime clusters are `NTT.js` generated method argument mapping, same-entity method response handling, and parent/child social update assumptions. They are central to schema bootstrap, method execution, favorite/like UI, comments, and list refresh behavior. These should be fixed only after narrow reproductions decide the intended contract.

## Failure Cluster Classification

### Vitest Import-Level Failures

The `ntx-favorites` and `ntx-logs` failures are most likely infrastructure/stale-test placement, not product regressions in `n3tx-ui`. The tests import package-relative component paths (`tests/frontend/tests/components/ntx-favorites.test.js:28`, `tests/frontend/tests/components/ntx-logs.test.js:35`), and Vitest rewrites `../../components/` to the `n3tx-ui` package component directory (`tests/frontend/vitest.config.js:31`). Those files are example-local surfaces, not package components.

Minimal fix target: decide ownership. Either move these tests under an example/static harness with aliases to `examples/core/static/components`, or promote the components into `n3tx-ui` intentionally. Do not add package shims just to satisfy stale imports without an ownership decision.

### Component Expectation Mismatches

These are mostly stale assertions:

| Component | Test expectation | Current behavior | Classification |
|---|---|---|---|
| `Component` | Five sizes only (`tests/frontend/tests/core/Component.test.js:73`) | Six modes including `row` (`packages/n3tx-core/src/n3tx_core/static/core/Component.js:26`) | Stale test |
| `ntx-ref-picker` | Inline `<style>` (`tests/frontend/tests/components/ntx-ref-picker.test.js:382`) | Linked CSS file (`packages/n3tx-ui/src/n3tx_ui/static/components/ntx-ref-picker.js:87`) | Stale test |
| `ntx-profile` | `.placeholder` node (`tests/frontend/tests/components/ntx-profile.test.js:159`) | `.profile-note` node (`packages/n3tx-ui/src/n3tx_ui/static/components/ntx-profile.js:54`) | Stale test or copy/DOM decision |
| `ntx-row` | Save call through a value test double (`tests/frontend/tests/components/ntx-row.test.js:125`) | Real path validates current component through Formidable (`packages/n3tx-ui/src/n3tx_ui/static/components/ntx-row.js:135`) | Brittle test or validation mismatch |

Minimal fix target: update stale DOM assertions after confirming current docs. For `ntx-row`, add a narrow test around `Formidable.validateForm` call shape before changing component code.

### Schema Bootstrap Like/Favorite Mismatch

This is a stale assertion. Product social action is `favorite`/`favorites`; comment social action is `like`/`likes`. The core docs show Product `favorites` and `favorite()` (`docs/CORE.md:78`, `docs/CORE.md:83`), and the mock Product schema follows that (`tests/frontend/tests/integration/helpers/mock-schemas.js:108`, `tests/frontend/tests/integration/helpers/mock-schemas.js:140`). The failing expectation that Product instances expose `like` is wrong (`tests/frontend/tests/integration/schema-bootstrap.test.js:74`, `tests/frontend/tests/integration/schema-bootstrap.test.js:79`).

Minimal fix target: tests. Rename Product method expectations to `favorite`; keep `like` expectations for `Comment` fixtures.

### Playwright Server Startup Failures

The likely failures here are infrastructure, not product regression:

| Suite | Startup risk | Evidence | Minimal fix target |
|---|---|---|---|
| Core | Marker file shell substitution couples setup/config ordering | `playwright.config.js:51`, `global-setup.js:37` | Harness |
| Grants | Wrong app path and DB env not propagated into webServer | `playwright.grants.config.js:34`, `grants-global-setup.js:27` | Harness decision |
| Veille | Same marker pattern; port/env in config only | `veille.playwright.config.js:51`, `veille.global-setup.js:27` | Harness |

Minimal fix target: create a shared run environment module or explicit generated env file used by both setup and config; disable reused servers by default for isolation-sensitive suites; update grants/perf to current app paths or remove them from default runner until maintained.

### Vitest Worker Out-Of-Memory

The OOM is likely infrastructure amplified by runtime singleton churn, not a direct product failure. The historical audit recorded two worker OOMs (`.project/plans/tests/full-test-failure-audit-2026-04-24.md:231`). The current config has no worker limit or memory guard (`tests/frontend/vitest.config.js:8`, `tests/frontend/vitest.config.js:16`), and multiple suites repeatedly reset modules and import runtime singletons (`tests/frontend/tests/integration/schema-bootstrap.test.js:17`, `tests/frontend/tests/integration/method-execution.test.js:16`, `tests/frontend/tests/integration/entity-lifecycle.test.js:16`).

Minimal fix target: harness first. Run import-heavy integration suites serially or with constrained workers, reduce per-test `vi.resetModules()` where a deterministic reset helper can clear NTT/Matrix state, and split package component tests from app/example tests.

## Highest-Risk Coverage Gaps

1. Generated method wrappers are not directly tested with real parameters. The implementation likely mishandles named parameters by reading `args[param]` from an array (`packages/n3tx-core/src/n3tx_core/static/core/NTT.js:731`, `packages/n3tx-core/src/n3tx_core/static/core/NTT.js:745`). Existing method tests mostly call `instance.call()` directly (`tests/frontend/tests/integration/method-execution.test.js:78`), so generated methods can be broken while tests pass.
2. Structured method responses need explicit tests for local social updates, child registration, duplicate prevention, and unfavorite/unlike removal. Implementation mutates arrays using `_field` and `id` (`packages/n3tx-core/src/n3tx_core/static/core/NTT.js:1040`, `packages/n3tx-core/src/n3tx_core/static/core/NTT.js:1058`), but tests mostly assert ambiguous responses trigger pull (`tests/frontend/tests/core/NTT.test.js:374`, `tests/frontend/tests/integration/entity-lifecycle.test.js:156`).
3. Playwright startup does not verify the server is using the seeded DB for that run. The server command reads a marker path (`tests/frontend/tests/e2e/playwright.config.js:51`), setup seeds a temp DB (`tests/frontend/tests/e2e/global-setup.js:25`, `tests/frontend/tests/e2e/global-setup.js:43`), but there is no sanity check after boot.
4. Example-local frontend components lack an explicit test home. Tests import them as if they were package components (`tests/frontend/tests/components/ntx-favorites.test.js:28`), but source lives outside package static dirs, creating import-level failures instead of meaningful contract tests.
5. Bad edge behavior can be canonized by tests. `ntx-ref-picker` expecting `undefineds` (`tests/frontend/tests/components/ntx-ref-picker.test.js:220`, `tests/frontend/tests/components/ntx-ref-picker.test.js:225`) is a concrete example where a test documents a bug-like fallback as desired behavior.

## Recommended Minimal Fix Sequence

1. Split the default frontend runner into maintained tiers or mark grants/perf as non-default until their configs are updated. Target `scripts/run-frontend-tests.py` and docs.
2. Fix Playwright app paths/env propagation before interpreting browser failures. Target `tests/frontend/tests/e2e/*.config.js` and setup/teardown pairs.
3. Move or re-alias example-local component tests so import-level failures disappear without changing product components blindly. Target tests/harness decision.
4. Update clearly stale component assertions: row mode in `Component`, linked CSS in `ntx-ref-picker`, `.profile-note` or chosen profile DOM contract, and Product `favorite` expectation.
5. Add narrow runtime tests for generated DynamicClass method wrappers and structured `_response_` social updates before editing `NTT.js`.
6. Add a Vitest memory/isolation pass: constrain workers for import-heavy suites, reduce repeated module resets where possible, and document which suites require fresh runtime singleton state.

## Residual Risks

Even after stale assertions are cleaned up, browser-visible social/comment/favorite failures may still contain real product regressions because they depend on method rendering, auth, schema hints, and `_response_` refresh behavior. Treat them as mixed until the runtime/generated-method tests are green.

The aggregate command should not be used as the primary signal for product correctness until grants/perf startup paths are repaired or excluded. In its current shape, a red `python3 scripts/run-frontend-tests.py` run can mean missing files, stale component contracts, wrong server roots, memory pressure, or actual UI regressions.
