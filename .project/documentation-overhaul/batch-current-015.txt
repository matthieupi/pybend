439: ## Update Resource
440: 
441: Update an existing resource.
442: 
443: > **Generated-route contract:** HTTP `PUT` is patch-oriented. Omitted fields
444: > remain unchanged. Supplied fields are merged with the current entity and the
445: > complete result is validated through the original model before only the
446: > supplied fields are persisted.
447: 
448: ### Request
449: 
450: ```
451: PUT /{resource}/{id}
452: ```
453: 
454: **Path Parameters**:
455: - `id` (integer, required): Resource ID
456: 
457: **Query Parameters**: None
458: 
459: **Request Headers**:
460: - `Content-Type: application/json` (required)
461: 
462: **Request Body**: Partial writable model representation
463: 
464: ```json
465: {
466:   "name": "Alice Johnson",
467:   "email": "alice@example.com",
468:   "age": 29
469: }
470: ```
471: 
472: **Update Behavior**:
473: - Omitted fields remain unchanged, including required and defaulted fields
474: - The merged complete entity must pass the original model's validation
475: - An explicit `[]` or `{}` replaces/clears the complete stored field
476: - Do not send the `id` field; identity comes from the route
477: - Backend-owned protected fields are stripped
478: - Foreign keys can be updated by passing new ID
479: 
480: For append/remove/toggle behavior on relationship collections, prefer a
481: domain-specific `@expose_route` method instead of client-side array replacement.
482: 
483: ### Response
484: 
485: **Success Status**: 200 OK
486: 
487: **Success Body**: Updated resource (complete object) with `$schema` and `$id`
488: 
489: ```json
490: {
491:   "$schema": "http://localhost:8000/User",
492:   "$id": "http://localhost:8000/User/1",
493:   "id": 1,
494:   "name": "Alice Johnson",
495:   "email": "alice@example.com",
496:   "age": 29
497: }
498: ```
499: 
500: **Error Responses**:
501: 
502: | Status | Cause | Detail |
503: |--------|-------|--------|
504: | 404 | Resource not found | `"Not found"` |
505: | 400 | Validation error | Custom validation message |
506: | 422 | Invalid field type | `"Invalid field 'age': ..."` |
507: 
508: ### Example

510: ```javascript

515:   const response = await fetch(`http://localhost:8000/users/${userId}`, {
516:     method: 'PUT',
517:     headers: {
518:       'Content-Type': 'application/json'
519:     },
520:     body: JSON.stringify({ ...writable, email: newEmail })

749: ## Collection Routes
750: 
751: When join models are registered (e.g., `ProductComment`, `ProductLike`), N3TX generates **collection routes** that return all child records across all parents.
752: 
753: ### Pattern
754: 
755: ```
756: GET /{parent_table}/{child_table}
757: ```
758: 
759: ### Examples
760: 
761: | Route | Returns |
762: |-------|---------|
763: | `GET /products/comments` | All comments across all products |
764: | `GET /products/likes` | All favorites across all products |
765: 
766: ### Response
767: 
768: Collection routes support the same pagination as regular list endpoints:
769: 
770: ```bash
771: # All comments (unpaginated)
772: GET /products/comments
773: 
774: # Paginated
775: GET /products/comments?limit=20&offset=0
776: ```
777: 
778: Response format matches the standard list endpoint (plain array without params, `{data, meta}` with pagination).
779: 
780: **Note**: Collection routes are registered before CRUD routes (Pass 1) to avoid path conflicts with `{id:int}` segments. This ensures `/products/comments` is not interpreted as `/products/{id}` with `id="comments"`.

1: # Custom Endpoints
2: 
3: Beyond standard CRUD operations, N3TX models can expose custom business logic through the `@expose_route` decorator. This document explains how these custom endpoints work from a frontend perspective.
4: 
5: ## Overview
6: 
7: Custom endpoints are defined in model classes using `@expose_route`:
8: 
9: ```python
10: @expose_route('/login', methods=['POST'])
11: def login(email: str, password: str) -> User:
12:     # Custom logic
13:     return user
14: ```
15: 
16: The decorator creates an HTTP endpoint that frontend can call.
17: 
18: ---
19: 
20: ## Endpoint URL Patterns
21: 
22: Custom endpoint URLs depend on the method type:
23: 
24: | Method Type | URL Pattern | Example |
25: |-------------|-------------|---------|
26: | **Static Method** | `/{resource}{custom_path}` | `POST /users/login` |
27: | **Class Method** | `/{resource}{custom_path}` | `GET /users/search` |
28: | **Instance Method** | `/{resource}/{id}{custom_path}` | `POST /products/1/discount` |
29: 
30: ### Static Method
31: 
32: Called on the model class, not on a specific instance.
33: 
34: **Backend**:
35: ```python
36: @staticmethod
37: @expose_route('/login', methods=['POST'])
38: def login(email: str, password: str) -> User:
39:     users = User.list()
40:     return next(u for u in users if u.email == email)
41: ```
42: 
43: **Frontend**:
44: ```javascript
45: // POST /users/login
46: const user = await fetch('http://localhost:8000/users/login', {
47:   method: 'POST',
48:   headers: { 'Content-Type': 'application/json' },
49:   body: JSON.stringify({
50:     email: 'alice@example.com',
51:     password: 'secret123'
52:   })
53: }).then(r => r.json());
54: ```
55: 
56: ### Class Method
57: 
58: Called on the model class, has access to `cls`.
59: 
60: **Backend**:
61: ```python
62: @classmethod
63: @expose_route('/search', methods=['GET'])
64: def search(cls, query: str) -> List[User]:
65:     return [u for u in cls.list() if query in u.name]
66: ```
67: 
68: **Frontend**:
69: ```javascript
70: // GET /users/search
71: const users = await fetch('http://localhost:8000/users/search', {
72:   method: 'GET',  // Note: Even though backend uses GET, you must POST with body
73:   headers: { 'Content-Type': 'application/json' },
74:   body: JSON.stringify({
75:     query: 'alice'
76:   })
77: }).then(r => r.json());
78: ```
79: 
80: **Important**: Custom endpoints always require JSON body, even if declared as GET.
81: 
82: ### Instance Method
83: 
84: Operates on a specific resource instance (requires ID in path).
85: 
86: **Backend**:
87: ```python
88: @expose_route('/discount', methods=['POST'])
89: def apply_discount(self, percentage: float) -> Product:
90:     self.price = self.price * (1 - percentage / 100)
91:     self.save()
92:     return self
93: ```
94: 
95: **Frontend**:
96: ```javascript
97: // POST /products/1/discount
98: const updated = await fetch('http://localhost:8000/products/1/discount', {
99:   method: 'POST',
100:   headers: { 'Content-Type': 'application/json' },
101:   body: JSON.stringify({
102:     percentage: 10
103:   })
104: }).then(r => r.json());
105: 
106: console.log('New price:', updated.price);
107: ```

111: ## Automatic User Injection
112: 
113: Custom methods can receive the authenticated user automatically by declaring a `user` parameter. The route layer bridges the auth-layer identity (JWT dict) to the model-layer entity, respecting the separation of concerns between the `authorize` package and N3TX models.
114: 
115: ### How It Works
116: 
117: When a custom method declares a `user` parameter, the route handler:
118: 
119: 1. Skips `user` during request body parsing (it's never read from the POST body)
120: 2. Extracts the JWT identity from the request (`request.state.user`)
121: 3. Resolves the type based on the parameter's type hint:
122:    - **Model class** (e.g., `User`) — fetches the full model instance via `User.get(user_id)`
123:    - **`dict`** — passes the raw JWT payload `{"user_id", "email", "role"}`
124:    - **No type hint** — passes the raw JWT dict
125: 
126: ### Example
127: 
128: **Backend**:
129: ```python
130: from .user_model import User

### docs/API_CUSTOM_ENDPOINTS.md (1103 total lines)
131: 
132: class Product(ProtoModel):
133:     @expose_route('/comment', methods=['POST'])
134:     def comment(self, comment: Comment, user: User = None) -> Comment:
135:         comment.user_owner = user.id if user else 1
136:         created = Comment.create(comment)
137:         self.update({'comments': [*(self.comments or []), created]})
138:         return created
139: ```
140: 
141: **Frontend** — `user` is NOT included in the request body:
142: ```javascript
143: // POST /products/1/comment
144: await fetch('http://localhost:8000/products/1/comment', {
145:   method: 'POST',
146:   headers: {
147:     'Content-Type': 'application/json',
148:     'x-access-token': jwtToken
149:   },
150:   body: JSON.stringify({
151:     comment: { name: "Great product!" }
152:     // No "user" field — injected server-side from JWT
153:   })
154: });
155: ```
156: 
157: ### Design: Auth/Model Boundary
158: 
159: The `authorize` package is standalone — it speaks plain dicts (`{"user_id", "email", "role"}`) and has zero N3TX model imports. The `_resolve_user()` bridge in the route layer translates between these two worlds:
160: 
161: ```
162: JWT Middleware (authorize)          Route Layer (_resolve_user)         Model Layer
163: ─────────────────────────          ─────────────────────────          ─────────────
164: request.state.user =          →    type hint is User?            →    User.get(user_id)
165:   {"user_id": 1,                     Yes → fetch model instance        → full User instance
166:    "email": "alice@...",             No  → pass raw dict               → plain dict
167:    "role": "user"}
168: ```
169: 
170: This keeps the auth package decoupled from models while giving model methods access to the full entity when needed.
171: 
172: ### Rules
173: 
174: - `user` is a reserved parameter name — never included in request body parsing
175: - The `user` parameter should have a default of `None` for unauthenticated endpoints
176: - Works in both instance methods (`post_with_id`) and class/static methods (`post_no_id`)
177: - The type hint drives resolution: `User` → model instance, `dict` → raw JWT payload

185: the request payload and receive an authorized `File` instance at invocation time.
186: 
187: ```python
188: from n3tx_files import File
189: 
190: class Transcriber(ActorModel):
191:     __tablename__ = 'transcribers'
192:     __storable__ = False
193: 
194:     @expose_route('/transcribe', methods=['POST'])
195:     async def transcribe(audio: File) -> dict:
196:         local = await audio.ensure_local()
197:         return {'path': local['path']}
198: ```
199: 
200: Request body:
201: 
202: ```json
203: {"audio": "http://localhost:5000/File/1"}
204: ```
205: 
206: The value must be the canonical absolute `$id` of a File on the current API.
207: 
208: Rules:
209: 
210: - Materialization is type-gated: only parameters annotated as `File` resolve.
211: - Plain `str` parameters receive the original string unchanged.
212: - `File.resolve()` enforces `read` access before returning the metadata record.
213: - Byte download remains explicit through `download` routes or `ensure_local()`;
214:   materialization itself resolves metadata, not arbitrary external bytes.

218: ## Request Format
219: 
220: ### HTTP Method
221: 
222: Custom endpoints can specify their HTTP method via the decorator:
223: ```python
224: @expose_route('/action', methods=['POST'])  # POST
225: @expose_route('/data', methods=['GET'])     # GET (but still requires body)
226: ```
227: 
228: **Frontend Impact**: Always use the specified HTTP method in `fetch()`.
229: 
230: ### Request Body
231: 
232: All custom endpoints require a JSON request body containing the method parameters.
233: 
234: **Parameter Mapping**:
235: 
236: Backend method signature:
237: ```python
238: def custom_method(self, name: str, age: int, active: bool = True):
239:     pass
240: ```
241: 
242: Frontend request body:
243: ```json
244: {
245:   "name": "Alice",
246:   "age": 28,
247:   "active": false
248: }
249: ```
250: 
251: **Rules**:
252: - Parameter names must match exactly (case-sensitive)
253: - All parameters without defaults are required
254: - Parameters with defaults are optional
255: - `self`, `cls`, and `user` are never included in request body (see [Automatic User Injection](#automatic-user-injection))
