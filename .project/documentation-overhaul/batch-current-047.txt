285: ### How it flows through the stack
286: 
287: Follow the data from model to pixel:
288: 
289: ```
290: 1. Model Definition (Python)
291:    Product(ProtoModel) with fields, __ui__, __access__, @expose_route
292:                     |
293: 2. Schema Generation (Backend)
294:    ProtoModel.schema() -> Pydantic JSON Schema + methods + access + ui + $defs
295:                     |
296: 3. Schema Endpoint
297:    GET /Product -> JSON response (public, no auth required)
298:                     |
299: 4. Frontend Bootstrap
300:    N3TX.SCHEMA(data) -> prototype() -> DynamicClass
301:    |  Creates typed class with getters, setters, callable methods
302:    |  Registers nested $defs as additional DynamicClasses
303:                     |
304: 5. Component Rendering
305:    |  form.js reads schema.properties -> builds form HTML
306:    |  Permissions.js reads schema.access -> shows/hides controls
307:    |  <ntx-method> reads schema.methods -> renders action buttons
308:    |  ntx-router reads schema.ui.renderer -> resolves navigation targets
309:                     |
310: 6. Entity Responses
311:    model_response() injects $schema + $id per record (via proto_dump pipeline)
312:    |  Every entity is self-describing and independently resolvable
313:    |  Local collection fields return hydrated child objects with `$schema`/`$id`

432: ## 🤖 Agents
433: 
434: Here's where things get really interesting. N3TX includes an LLM-powered agent system built on [Pydantic AI](https://ai.pydantic.dev/). Every Actor with `@expose_route` methods is a tool collection, and an Agent is an Actor that reasons.
435: 
436: ### Dynamic Agents (primary path)
437: 
438: Agents are instances of `AgentActor` -- configuration is data, not code. You define them like any other model instance:
439: 
440: ```python
441: from n3tx_agents import AgentActor
442: 
443: scanner = AgentActor(
444:     name="Grant Scanner",
445:     prompt="You find government grants...",
446:     tools=["grants", "web_tools"],
447:     llm="anthropic:claude-sonnet-4-5-20250929",
448:     constraints={"max_iterations": 30},
449: )
450: 
451: result = await scanner.agentic(task="Find grants about renewable energy")
452: ```
453: 
454: Agents can be created via API (`POST /agents`), stored in the database, and triggered via `POST /agents/{id}/agentic`. Yeah, your agents are just data -- create, update, and delete them like any other resource.
455: 
456: ### Agentic Model Methods (secondary path)
457: 
458: Any model with `__agent__ = True` gains LLM reasoning capabilities. One flag, and your model can think:
459: 
460: ```python
461: class Product(ActorModel):
462:     __agent__ = True
463: 
464: # Class-level: reasons about the schema
465: result = await Product.agentic(task='What fields does Product have?')
466: 
467: # Instance-level: reasons about schema + this specific record
468: product = Product.get(1)
469: result = await product.agentic(task='Is this product priced competitively?')
470: 
471: # Streaming
472: async for chunk in product.agentic_stream(task='Describe this product'):
473:     print(chunk['data'], end='', flush=True)
474: ```
475: 
476: Tool calls route through Matrix as TX messages, preserving auth and interceptors.

542: ## 🧰 Extending the Application
543: 
544: N3TX is designed to get out of your way when you want to customize.
545: 
546: ### Add a New Model
547: 
548: 1. Subclass `ProtoModel` (or `ActorModel` for actor capabilities)
549: 2. Set `__storable__ = True` for persistence
550: 3. Use `@expose_route()` for custom API endpoints
551: 4. Register with `register_model(...)` or pass to `create_app(models=[...])`
552: 
553: ### Add Relationships
554: 
555: ```python
556: class OwnerModel(ProtoModel):
557:     __tablename__ = 'owners'
558:     __storable__ = True
559:     children: list[SubModel] = Field(default=[])
560: 
561: register_model(OwnerModel, storage=backend)
562: register_model(SubModel, storage=backend)
563: ```
564: 
565: ### Update Safety
566: 
567: Generated direct and actor HTTP `PUT` routes, direct `Model.update(id, patch)`,
568: raw actor TX updates, and agent update tools share one partial-update contract.
569: Omitted fields remain unchanged. Supplied collections are complete replacements
570: and writes are last-write-wins; prefer domain methods for append/remove/toggle
571: operations.
572: See [CRUD update semantics](../../docs/API_CRUD_ENDPOINTS.md#update-resource).
573: 
574: ### Add a Storage Backend
575: 
576: 1. Implement `AbstractStorage` methods (`create_table`, `create`, `get`, `list`, `update`, `delete`)
577: 2. Inject via `set_storage()` or pass to `register_model()`
578: 
579: Want something beyond SQLite and JSON? The interface is simple -- implement six methods and you're in business.

608: ## 🧭 Key Patterns
609: 
610: These are the principles that make N3TX click. Keep them in mind and everything will feel natural:
611: 
612: 1. **The model is the app.** Define a `ProtoModel` subclass with `__tablename__`, `__storable__`, fields, and `@expose_route` methods. The framework derives CRUD endpoints, JSON Schema, DB tables, forms, and permissions automatically.
613: 
614: 2. **Schema is the contract.** `GET /ClassName` returns a JSON Schema carrying types, validation, UI hints, access rules, and method signatures. The frontend reads this at runtime and adapts -- no frontend code changes needed.
615: 
616: 3. **Incremental adoption.** Start with `n3tx-core` alone (models + direct routes). Add `n3tx-actors` when you need messaging. Add `n3tx-agents` when you need LLM reasoning. Add `n3tx-ui` when you want the auto-generated frontend. Add `n3tx-files` when your app needs uploaded documents, media, or artifacts.
617: 
618: 4. **Access control propagates.** Set `__access__` on a model, and the rules flow through schema to the frontend. Edit/delete buttons appear or disappear based on the authenticated user's permissions.
619: 
620: 5. **`create_app` and `N3TXApp` live in `n3tx_core.app`.** They are not star-exported from the meta-package. Always import them explicitly: `from n3tx_core.app import create_app`.
