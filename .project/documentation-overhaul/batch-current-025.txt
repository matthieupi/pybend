### docs/JSON_FIELDS.md (377 total lines)
1: # N3TX JSON Fields
2: 
3: This guide explains how N3TX stores `dict` and `list` model fields as JSON,
4: when to use them, how they differ from relationships, and which implementation
5: points agents and developers should inspect before changing this part of the
6: system.
7: 
8: ## Mental Model
9: 
10: JSON fields are ordinary model fields whose Python value is a `dict` or `list`,
11: but whose SQLite representation is a `TEXT` column containing serialized JSON.
12: 
13: ```text
14: Model annotation
15:   -> get_json_fields(model_class)
16:   -> SQLite TEXT column
17:   -> json.dumps(value, default=str) on write
18:   -> json.loads(value) on read
19:   -> Pydantic validation / model instance
20: ```
21: 
22: Example:
23: 
24: ```python
25: from pydantic import Field
26: from n3tx_core.models.proto_model import ProtoModel
27: 
28: 
29: class AgentConfig(ProtoModel):
30:     __tablename__ = "agent_configs"
31:     __storable__ = True
32: 
33:     tools: list[str] = Field(default=[])
34:     constraints: dict = Field(default={})
35:     metadata: dict = Field(default={})
36: ```
37: 
38: SQLite stores these fields as text:
39: 
40: ```text
41: tools        TEXT -> '["search", "scrape"]'
42: constraints  TEXT -> '{"max_iterations": 30}'
43: metadata     TEXT -> '{"provider": "ollama", "nested": {"ok": true}}'
44: ```
45: 
46: The storage layer deserializes them before model construction, so application
47: code sees normal Python values:
48: 
49: ```python
50: config.tools == ["search", "scrape"]
51: config.constraints == {"max_iterations": 30}
52: ```
53: 
54: ## Supported Field Shapes
55: 
56: JSON field detection is implemented by
57: `n3tx_core.utils.introspection.get_json_fields()`.
58: 
59: | Annotation | JSON TEXT field? | Notes |
60: |---|---:|---|
61: | `dict` | Yes | Stored with `json.dumps()` |
62: | `Dict[str, Any]` | Yes | Any `dict` origin is included |
63: | `Optional[dict]` | Yes | `typing.Optional` / `typing.Union` is unwrapped |
64: | `list` | Yes | Stored with `json.dumps()` |
65: | `List[str]`, `list[str]` | Yes | Primitive typed lists are JSON fields |
66: | `List[int]`, `list[int]` | Yes | Primitive typed lists are JSON fields |
67: | `list[T: ProtoModel]` | Yes | Ordered local id list, hydrated into child objects |
68: | `list[Ref[T]]` | Yes | Pointer/ref list |
69: | `ManyToMany[T]` | No | Legacy shared-link helper; prefer explicit link models |
70: 
71: Use the current, test-backed style for nullable JSON fields:
72: 
73: ```python
74: from typing import Optional
75: 
76: config: Optional[dict] = Field(default=None)
77: ```
78: 
79: Avoid assuming every newer union spelling is handled equally in all storage and
80: migration paths unless there is a test for it.
81: 
82: ## JSON Field vs Relationship Field
83: 
84: The most important distinction is whether the nested data needs independent
85: identity and lifecycle.
86: 
87: ```python
88: # JSON field: embedded data, no identity
89: tags: list[str] = Field(default=[])
90: payload: dict = Field(default={})
91: 
92: # Local relationship field: child resources with identity, auth, hydration
93: comments: list[Comment] = Field(default=[])
94: ```
95: 
96: | Concern | Embedded JSON | `list[T]` local relationship |
97: |---|---|---|
98: | Storage | One SQLite `TEXT` column | JSON id list on the parent row |
99: | API identity | No nested `$id` | Child resources keep flat class-name `$id` |
100: | Access control | Whole field only | Per child resource possible |
101: | Updates | Replace whole field | Replace ordered id list; child rows update independently |
102: | Querying | No first-class nested query API | Query child model through its own collection route |
103: | Schema | Pydantic property schema | Full model schema and `$defs` |
104: | Good for | Config, metadata, payloads | Comments, likes, children, owned records |
105: 
106: Rule of thumb:
107: 
108: - Use JSON fields for simple embedded values that belong entirely to the parent.
109: - Use models and relationships when the nested thing should be addressable,
110:   authorized, queried, rendered, or updated independently.
111:

### docs/JSON_FIELDS.md (377 total lines)
131: 
132: Important behavior:
133: 
134: - Python `dict` and `list` become JSON strings.
135: - Nested dict/list structures are serialized recursively.
136: - Non-JSON-native nested values are converted with `default=str`.
137: - Other non-SQLite-native top-level values also fall back to `str()`.
138: 
139: Example:
140: 
141: ```python
142: Job.create({
143:     "name": "scan",
144:     "payload": {
145:         "source": "api",
146:         "params": {"q": "renewable grants"},
147:         "tags": ["energy", "funding"],
148:     },
149: })
150: ```
151: 
152: ## Read Path
153: 
154: Implementation:
155: 
156: ```text
157: packages/n3tx-core/src/n3tx_core/storage/sqlite_storage.py
158: ```
159: 
160: Key function:
161: 
162: ```python
163: def _deserialize_json_fields(model_class, record):
164:     for field_name in get_json_fields(model_class):
165:         val = record.get(field_name)
166:         if isinstance(val, str):
167:             try:
168:                 record[field_name] = json.loads(val)
169:             except (json.JSONDecodeError, TypeError):
170:                 pass
171: ```
172: 
173: This runs before model instantiation in the main read paths:
174: 
175: - `SQLiteStorage.get()`
176: - `SQLiteStorage.list()`
177: - relationship population paths inside `_populate_fields()`
178: 
179: If a stored value is not valid JSON, the helper leaves it unchanged. Pydantic may
180: still reject the resulting value if the model field requires `dict` or `list`.
181: 
182: ## Migration Behavior
183: 
184: Implementation:
185: 
186: ```text
187: packages/n3tx-core/src/n3tx_core/storage/sqlite_migration.py
188: ```
189: 
190: During table creation:
191: 
192: - `dict` fields become `TEXT` columns.
193: - `list` fields become `TEXT` columns.
194: - `list[T: ProtoModel]` stores ordered local child ids in the parent row.
195: - `ManyToMany[T]` is a legacy shared-link helper and is not stored as a parent
196:   JSON list.
197: 
198: During auto-migration:
199: 
200: - new `dict` fields are added as `TEXT DEFAULT '{}'`.
201: - new `list` fields are added as `TEXT DEFAULT '[]'`.

254: ## Tradeoffs and Gotchas
255: 
256: ### JSON fields are not independently addressable
257: 
258: Nested JSON values do not get routes, `$id`, lifecycle events, ownership, or
259: per-item authorization.
260: 

### docs/JSON_FIELDS.md (377 total lines)
261: If a nested value should be a resource, model it as a `ProtoModel`/`ActorModel`
262: and reference it with `list[T]`, `Ref[T]`, or an explicit link model.
263: 
264: ### Updates replace the whole field
265: 
266: Partial updates do not deep-merge JSON fields.
267: 
268: ```python
269: Job.update(1, {"payload": {"status": "done"}})
270: ```
271: 
272: This replaces `payload`; it does not preserve other keys from the previous
273: payload unless the caller includes them.
274: 
275: ### Generated HTTP PUT preserves omitted collections
276: 
277: The Python update API is patch-oriented, so omitting a JSON field leaves it
278: unchanged:
279: 
280: ```python
281: Job.update(1, {"title": "Renamed"})  # payload is not supplied or replaced
282: ```
283: 
284: Generated HTTP `PUT` routes use the same patch contract. Downstream clients may
285: send only changed fields:
286: 
287: ```json
288: {
289:   "title": "Renamed"
290: }
291: ```
292: 
293: An omitted JSON field remains unchanged. An explicit `[]` or `{}` means replace
294: the complete stored field with an empty value. The same rule applies to
295: JSON-backed `list[T]` local relationship IDs and `list[Ref[T]]` pointer arrays.
296: 
297: ### There is no first-class nested JSON query API
298: 
299: N3TX currently treats these as serialized text fields. The framework does not
300: provide a public query builder for expressions like:
301: 
302: ```sql
303: json_extract(payload, '$.status') = 'queued'
304: ```
305: 
306: If an application needs first-class filtering, sorting, or indexing by nested
307: properties, prefer explicit model fields or related models.
308: 
309: ### `default=str` is convenient but lossy
310: 
311: `json.dumps(..., default=str)` prevents many serialization crashes, but it can
312: silently convert rich values into strings.
313: 
314: Examples:
315: 
316: | Python value | Stored JSON value |
317: |---|---|
318: | `datetime.datetime(...)` | string timestamp representation |
319: | `AnyHttpUrl(...)` | URL string |
320: | custom object | `str(object)` |
321: 
322: Use explicit field types when round-trip fidelity matters.
323: 
324: ### Invalid stored JSON is tolerated, not repaired
325: 
326: `_deserialize_json_fields()` leaves invalid JSON strings unchanged. This avoids
327: masking or rewriting corrupted data, but Pydantic validation may fail later.
328: 
329: ### Mutable defaults rely on Pydantic behavior
330: 
331: Existing examples use `Field(default=[])` and `Field(default={})`. Pydantic v2
332: handles model defaults safely for normal model construction, but new code may
333: still prefer `default_factory=list` or `default_factory=dict` when that improves
334: clarity.

349: ## Change Checklist
350: 
351: When changing JSON-field behavior:
352: 
353: 1. Preserve the relationship boundary: `list[T]` stores ordered local ids,
354:    `list[Ref[T]]` stores pointer refs, and `ManyToMany[T]` remains a legacy
355:    shared-link helper.
