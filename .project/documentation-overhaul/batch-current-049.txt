47: ## 1. Mental Model — The Big Picture
48: 
49: N3TXTX is an **actor-based** frontend runtime. Think of it as a post office
50: inside the browser: every piece of data, every UI component, and the network
51: layer are all **actors** with mailboxes. They communicate by sending
52: **TX messages** through a central router called the **Matrix**.
53: 
54: ```
55: +-------------------------------------------------------------------+
56: |                        BROWSER                                     |
57: |                                                                    |
58: |   +-----------+     TX Messages     +-----------------------+      |
59: |   |   UI      | <=================> |      MATRIX           |      |
60: |   |  Layer    |   (ATTACH, UPDATE,  |   (Root Actor /       |      |
61: |   |           |    DESCRIBE, ...)   |    Message Router)     |      |
62: |   | <ntx-list |                     |                       |      |
63: |   | <ntx-item |                     |   children:           |      |
64: |   +-----------+                     |   +- N3TX (registry)   |      |
65: |                                     |   +- Product (DynClass)|     |
66: |                                     |   +- Component (UI)   |      |
67: |                                     |   +- ...              |      |
68: |                                     +----------+------------+      |
69: |                                                |                   |
70: |                                     +----------v-----------+       |
71: |                                     | NetworkAdapter       |       |
72: |                                     | (HTTP / WebSocket)   |       |
73: |                                     +----------+-----------+       |
74: +------------------------------------+-----------+-------------------+
75:                                      |  fetch() / WS
76:                                      +----------v-----------+
77:                                      |   N3TX Backend     |
78:                                      |   (FastAPI)          |
79:                                      |                      |
80:                                      |  GET /Product        | -> JSON Schema
81:                                      |  GET /products       | -> [{...}, ...]
82:                                      |  PUT /products/1     | -> Updated record
83:                                      +----------------------+
84: ```
85: 
86: ### Key Insight: Components Never Talk to the Network Directly
87: 
88: A `<ntx-item>` doesn't call `fetch()`. It sends a TX message to its N3TX actor,
89: which routes through the Matrix, hits the NetworkAdapter, and the response
90: flows back the same way. This decouples UI from transport entirely.

189: ## 4. Core Concepts
190: 
191: ### The Four Pillars
192: 
193: ```
194: +---------+    +-----------+    +---------+    +-------------+
195: |  Matrix  |    |    N3TX    |    |   TX    |    |  Component  |
196: |          |    |           |    |         |    |             |
197: |  Root    |    | Registry  |    | Message |    | Web Comp.   |
198: |  Actor   |    | + Entity  |    |Envelope |    | = Actor     |
199: |  Router  |    | Base      |    |         |    |             |
200: |          |    |           |    |         |    |             |
201: +---------+    +-----------+    +---------+    +-------------+
202: ```
203: 
204: | Concept | What it is | Analogy |
205: |---------|-----------|---------|
206: | **Matrix** | Singleton root actor. Routes every TX message to the right place, or sends it to the backend. | The post office |
207: | **N3TX** | Named Transfer Type. Static level: type registry + universal ATTACH router. Instance level: per-entity data with `href` pointing at its backend URL. | A registry + data holder |
208: | **DynClass** | DynamicClass. One per model (e.g., `Product`). Runtime-generated N3TX subclass. Holds the JSON schema, manages entity instances, handles CRUD. Born complete — never half-initialized. | A typed class factory |
209: | **TX** | Transaction message. `{name, source, target, data, meta}`. Every interaction is a TX. | A letter in an envelope |
210: | **Component** | Web component base class that is also an Actor. Has `send()` and `inbox()`. | A mailbox-enabled HTML element |
211: 
212: ### Actor Hierarchy
213: 
214: ```
215: Matrix (root)
216:  +-- N3TX (class — type registry)
217:  +-- Product (DynClass — runtime-generated)
218:  |    +-- 1 (N3TX instance — Product/1)
219:  |    +-- 2 (N3TX instance — Product/2)
220:  |    +-- ...
221:  +-- User (DynClass)
222:  |    +-- ...
223:  +-- Component (class)
224:  |    +-- List-abc123 (instance)
225:  |    +-- Item-def456 (instance)
226:  |    +-- ...
227:  +-- TT (class)
228: ```
229: 
230: Every actor has:
231: - An **address** (`addr`) — e.g., `"Product"`, `"Product/1"`, `"Item-abc123"`
232: - An **inbox** — receives TX messages, dispatches to `this[tx.name](tx.data, tx)`
233: - A **send** method — routes TX to target (local child, or bubble to Matrix)
234: - **Children** — a map of child actors
235: 
236: ### Address Resolution
237: 
238: TX messages route through the tree using `/`-separated addresses:
239: 
240: ```
241: Target: "Product/1"
242: 
243: Matrix receives TX
244:   +-- "Product" in children? YES -> DynClass "Product"
245:   |     +-- "1" in children? YES -> N3TX instance
246:   |     |     +-- Delivered to N3TX inbox
247: ```
248: 
249: If the target is a URL (e.g., `http://localhost:5000/products`), Matrix
250: can't resolve it locally -> forwards to `NetworkAdapter.send()` -> HTTP request.

255: 
256: ### Sending a Message
257: 
258: ```js
259: // From any actor (component, N3TX, DynClass...):
260: this.send(new TX({

262:     source: this.addr,          // Sender's address
263:     target: 'Product/1',       // Recipient's address

267: 
268: ### Routing Algorithm
269: 
270: ```
271: Actor.send(tx)
272:   |
273:   +-- Is target a direct child?
274:   |     YES -> child.inbox(tx)
275:   |
276:   +-- Does target start with my addr?
277:   |     YES -> strip prefix, route to children
278:   |
279:   +-- Neither?
280:         -> Prefix source with my addr
281:         -> Bubble up to Matrix.inbox(tx)
282:               |
283:               +-- Is first segment of target in Matrix children?
284:               |     YES -> forward to that class/DynClass
285:               |
286:               +-- Unknown target?
287:                     -> NetworkAdapter.send(tx) -> HTTP/WS
288: ```
289: 
290: ### Receiving a Message
291: 
292: When a TX arrives at an actor's inbox:
293: 
294: ```js
295: // Actor._inbox dispatches by event name:
296: this[tx.name](tx.data, tx)
297: 
298: // Example: N3TX instance receives UPDATE
299: // -> calls this.UPDATE(data, event)
300: ```
301: 
302: **Convention:** Handler names are UPPERCASE and match the TX `name` field exactly.

543: ## 8. Local Relationship Hydration — Collection Fields as Objects
544: 
545: When a model has a local owned collection field (for example
546: `Product.comments: list[Comment]`), SQLite stores an ordered JSON array of child
547: ids on the parent row. On read, the backend hydrates those ids into
548: self-describing child objects. The frontend can render the relationship directly
549: while each child still carries its own flat class-name identity URL.
550: 
551: ### What the Data Looks Like
552: 
553: ```json
554: {
555:   "id": 1,
556:   "name": "Keyboard",
557:   "price": 49.99,
558:   "comments": [
559:     {
560:       "$schema": "http://localhost:5000/Comment",
561:       "$id": "http://localhost:5000/Comment/1",
562:       "id": 1,
563:       "name": "Great!",
564:       "description": "Love it"
565:     },
566:     {
567:       "$schema": "http://localhost:5000/Comment",
568:       "$id": "http://localhost:5000/Comment/2",
569:       "id": 2,
570:       "name": "Useful",
571:       "description": "Bought one too"
572:     }
573:   ]
574: }
575: ```
576: 
577: Each child object has the same identity shape as a top-level entity:
578: 
579: ```
580: {API_URL}/{ChildClassName}/{child_id}
581: ```
582: 
583: | Segment | Source | Example |
584: |---------|--------|---------|
585: | `API_URL` | `config.API_URL` | `http://localhost:5000` |
586: | `ChildClassName` | Child model class name | `Comment` |
587: | `child_id` | Child record ID | `2` |
588: 
589: ### Resolving Child Objects
590: 
591: Each child's `$id` is a standard class-name URL. Fetching it returns the full
592: child object:
593: 
594: ```
595: GET /Comment/1
596: -> { "$schema": "http://localhost:5000/Comment", "$id": "http://localhost:5000/Comment/1", "id": 1, "name": "Great!" }
597: ```
598: 
599: No generated nested routes are needed. Relationship ownership is represented by
600: the model field and storage contract, not by a parent-scoped URL segment.
601: 
602: ### Why Hydrated Objects
603: 
604: - **Schema-driven rendering** — relationship values already include `$schema` and `$id` metadata.
605: - **Flat identity** — every entity resolves through `/{ClassName}/{id}` regardless of where it appears.
606: - **Simpler storage** — owned local collection order is the parent row's JSON id array.
607: - **Model-first behavior** — app-specific append/toggle rules live in `@expose_route` methods.
608: 
609: ### Backend Type: `list[T]`
610: 
611: On the backend, local owned collection fields use normal Python list typing:
612: 
613: ```python
614: class Product(ProtoModel):
615:     comments: list[Comment] = Field(default=[])
616: ```
617: 
618: `list[T]` stores local child ids in SQLite and hydrates them into `T` instances
619: when the parent is read. Use `list[Ref[T]]` instead when the field is a pointer
620: array that may include distributed references.
621: 
622: ### Schema Representation
623: 
624: The JSON schema for a local `list[T]` field is an array of the child schema:
625: 
626: ```json
627: {
628:   "comments": {
629:     "type": "array",
630:     "items": { "$ref": "#/$defs/Comment" }
631:   }
632: }
633: ```
634: 
635: This tells the frontend that `comments` values are child objects. The backend
636: keeps those objects self-describing in API responses.
637:
