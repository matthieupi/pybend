55: ## Authentication (JWT)
56: 
57: ### How It Works
58: 
59: 1. User calls `POST /users/login` with email + password
60: 2. Server verifies credentials, returns a JWT token
61: 3. Client sends `x-access-token: <token>` header on every request
62: 4. `JWTAuthMiddleware` decodes the token and stores the payload in `request.state.user`
63: 
64: ### Token Payload
65: 
66: ```json
67: {
68:     "user_id": 1,
69:     "email": "alice@example.com",
70:     "role": "user",
71:     "exp": 1771678445,
72:     "iat": 1771592045
73: }
74: ```
75: 
76: The `role` field is read from the `User.role` model field and embedded in the token at login/register time.
77: 
78: ### Configuration
79: 
80: The package reads `JWT_SECRET` and `JWT_EXPIRY_HOURS` from environment variables by default. To override, call `configure()` at application startup:
81: 
82: ```python
83: import authorize
84: 
85: authorize.configure(
86:     jwt_secret="your-production-secret",
87:     jwt_expiry_hours=48,
88: )
89: ```
90: 
91: In N3TX, this is done in `main.py` using values from `config.py`.
92: 
93: ### Key Functions (`authorize/auth.py`)
94: 
95: | Function | Purpose |
96: |---|---|
97: | `configure(jwt_secret, jwt_expiry_hours)` | Set JWT config at startup |
98: | `hash_password(plain)` | Bcrypt hash for storage |
99: | `verify_password(plain, hashed)` | Bcrypt verification |
100: | `create_token(user_id, email, role)` | Creates a signed JWT |
101: | `decode_token(token)` | Validates and decodes a JWT |
102: 
103: ### Auth-Exempt Paths
104: 
105: The JWT middleware skips authentication for:
106: - `/login`, `/register`, `/docs`, `/openapi.json`, `/redoc`
107: - Static files: `.html`, `.js`, `.css`, `.png`, `.ico`, `.svg`, `.woff`, `.woff2`, `.ttf`
108: 
109: These are configured in `FastAPIBackend.AUTH_EXEMPT_PATHS` and `AUTH_EXEMPT_EXTENSIONS`.

113: ## Authorization (ABAC)
114: 
115: Authorization happens **after** authentication. The middleware verifies identity; the authorize layer decides what that identity can do.
116: 
117: ### Declaring Access Rules on Models
118: 
119: Add an `__access__` class variable mapping action names to rules:
120: 
121: ```python
122: class Comment(ProtoModel):
123:     __access__ = {
124:         'create': AUTHENTICATED,
125:         'read':   ANYONE,
126:         'list':   ANYONE,
127:         'update': OWNER,
128:         'delete': OWNER | ROLE('admin', 'moderator'),
129:     }
130:     __owner_field__ = 'user_owner'  # which field holds the owner's user ID

### docs/AUTHORIZATION.md (477 total lines)
131: ```
132: 
133: **Action names** correspond to CRUD operations: `create`, `read`, `list`, `update`, `delete`.
134: 
135: **Wildcard fallback:** Use `'*'` as a catch-all for any action not explicitly listed:
136: 
137: ```python
138: __access__ = {
139:     '*': AUTHENTICATED,          # default for all actions
140:     'delete': ROLE('admin'),     # override for delete
141: }
142: ```
143: 
144: **No `__access__` at all:** Falls back to `AUTHENTICATED` for all actions (backward compatible).
145: 
146: ### Protected Fields
147: 
148: Models can declare `__protected_fields__` to mark fields as backend-owned:
149: 
150: ```python
151: class Comment(ProtoModel):
152:     __protected_fields__: ClassVar[set] = {'user_owner'}
153:     __access__ = {
154:         'read': ANYONE,
155:         'create': AUTHENTICATED,
156:         'update': OWNER | ROLE('admin'),
157:         'delete': OWNER | ROLE('admin'),
158:     }
159: ```
160: 
161: **What protected fields do:**
162: 
163: | Layer | Behavior |
164: |-------|----------|
165: | **Create** | Route layer auto-injects `user_owner` from JWT payload (`user_id`) |
166: | **Update** | Route layer strips protected fields from incoming data — cannot be modified via API |
167: | **Schema** | Marked with `ui.protected = true` in JSON Schema properties |
168: | **Frontend** | `form.js` hides protected fields in edit mode; display mode shows them normally |
169: 
170: This ensures that ownership assignment is server-authoritative — clients can never set or change `user_owner` directly.
171: 
172: ### Declaring Access Rules on Methods
173: 
174: Custom methods use the `access=` parameter on `@expose_route()`:
175: 
176: ```python
177: @expose_route('/like', methods=['POST'], access=AUTHENTICATED)
178: def like(self) -> str: ...
179: 
180: @expose_route('/admin-reset', methods=['POST'], access=ROLE('admin'))
181: def admin_reset(self) -> str: ...
182: 
183: @expose_route('/login', methods=['POST'], access=ANYONE)
184: def login(email: str, password: str) -> dict: ...
185: ```
186: 
187: If no `access=` is provided, the method falls back to the model's `__access__` dict, then to `AUTHENTICATED`.
188: 
189: ### Built-in Rules
190: 
191: | Rule | Grants access when... | SQL filter |
192: |---|---|---|
193: | `ANYONE` | Always | `1=1` (no filter) |
194: | `AUTHENTICATED` | User has a valid JWT | `1=1` (middleware handles) |
195: | `OWNER` | `resource.{owner_field} == user.id` (handles FK-hydrated hrefs) | `{owner_field} = ?` |
196: | `ROLE('admin')` | `user.role == 'admin'` | `1=1` if match, `1=0` if not |
197: | `ROLE('a', 'b')` | `user.role in {'a', 'b'}` | Same |
198: | `Where(field=val)` | `resource.field == val` | `field = ?` |
199: 
200: ### Composing Rules
201: 
202: Rules compose with Python operators:
203: 
204: ```python
205: # OR: either condition grants access
206: OWNER | ROLE('admin')
207: 
208: # AND: both conditions must be true
209: OWNER & Where(status='draft')
210: 
211: # NOT: inverts the rule
212: ~ROLE('banned')
213: 
214: # Complex:
215: (OWNER | ROLE('admin')) & ~ROLE('suspended')
216: ```
217: 
218: Composites produce `OrRule`, `AndRule`, `NotRule` objects that evaluate recursively and generate combined SQL.
219: 
220: ### The Where Rule
221: 
222: `Where` checks resource attributes with optional comparison operators:
223: 
224: ```python
225: Where(status='published')           # status = 'published'
226: Where(price__lt=100)                # price < 100
227: Where(price__gte=50)                # price >= 50
228: Where(category__in=['A', 'B'])      # category IN ('A', 'B')
229: Where(status__ne='archived')        # status != 'archived'
230: ```
231: 
232: Supported operators: `__lt`, `__gt`, `__lte`, `__gte`, `__ne`, `__in`.

279: ### SQL Pushdown
280: 
281: For `list` operations, the authorization rule produces a SQL WHERE clause that is injected directly into the database query. This avoids loading all rows and filtering in Python.
282: 
283: ```python
284: # OWNER rule for user_id=5:
285: sql_filter = ("user_owner = ?", [5])
286: # Becomes: SELECT * FROM products WHERE user_owner = 5
287: 
288: # Composite OWNER | ROLE('admin') for an admin:
289: sql_filter = ("(user_owner = ?) OR (1=1)", [5])
290: # Simplifies to: all rows (admin sees everything)
291: 
292: # Where(visibility='public') for non-owner:
293: sql_filter = ("visibility = ?", ["public"])
294: # Becomes: SELECT * FROM products WHERE visibility = 'public'
295: ```
296: 
297: If a rule cannot produce SQL (returns `None` from `sql_filter()`), no filter is applied. Custom rules that can't express their logic as SQL should fall back to `None`.

326: ### Two-Tier Auth (Actor Routing — Level 3)
327: 
328: When using `create_app(routing='actor')`, authorization splits into two tiers:
329: 
330: **Tier 1: Protocol boundary interceptor** (`api/auth_interceptor.py`)
331: 
332: Registered on the NetworkAPI adapter via `api.use(auth_interceptor, on='request')`. Runs before the TX enters the actor system.
333: 
334: | Action | Behavior |
335: |--------|----------|
336: | `schema` | Pass-through (always public) |
337: | `list` | Compute `sql_filter` via `resolver.sql_filter_for()`, store in `tx.meta['sql_filter']` |
338: | `create` | Full rule check — no resource instance needed |
339: | `read`/`update`/`delete` | Identity gate only — unauthenticated users rejected if rule requires auth |
340: 
341: **Tier 2: Handler guard** (`models/actor_model.py → _authorize()`)
342: 
343: Runs inside `handler_crud()` after fetching the resource instance. Evaluates the full ABAC rule including OWNER checks (which need the actual entity to compare `user_owner` with `user_id`).
344: 
345: ```python
346: # Tier 2 checks happen at each CRUD step:
347: # create: _authorize('create', tx) before creating instance
348: # get:    fetch first, then _authorize('read', tx, resource=instance)
349: # list:   reads tx.meta['sql_filter'] from Tier 1
350: # update: fetch first, _authorize('update', tx, resource=instance)
351: # delete: fetch first, _authorize('delete', tx, resource=instance)
352: ```
353: 
354: **Why two tiers?** OWNER rules need the resource instance. The interceptor runs before the handler fetches it. The handler guard runs after. This natural split means:
355: - Tier 1: fast rejection of unauthenticated/unauthorized at the boundary
356: - Tier 2: resource-dependent checks (OWNER, Where) inside the handler
357: 
358: **Level 1/2 routing** (`routes_fastapi.py`) continues to use its existing single-pass auth via `_resolver.authorize(ctx)` — unchanged.
359: 
360: ### The Resolver Protocol
361: 
362: The `DefaultResolver` is one implementation of the `AuthorizationResolver` protocol:
363: 
364: ```python
365: class AuthorizationResolver(Protocol):
366:     def resolve_rule(self, model_class, action: str) -> AccessRule: ...
367:     def authorize(self, ctx: AccessContext) -> None: ...
368:     def sql_filter_for(self, ctx: AccessContext) -> tuple[str, list] | None: ...
369: ```
370: 
371: The resolver is instantiated once in `routes_fastapi.py` as `_resolver = DefaultResolver()`. To swap strategies, replace that single line.

420: ### Swapping the Resolver
421: 
422: To add DB-stored policy overrides, implement the protocol:
423: 
424: ```python
425: class OverrideResolver:
426:     def __init__(self, base_resolver, override_store):
427:         self.base = base_resolver
428:         self.store = override_store
429: 
430:     def resolve_rule(self, model_class, action):
431:         override = self.store.get(model_class.__tablename__, action)
432:         if override:
433:             return override
434:         return self.base.resolve_rule(model_class, action)
435: 
436:     def authorize(self, ctx):
437:         rule = self.resolve_rule(ctx.model_class, ctx.action)
438:         if not rule.evaluate(ctx):
439:             raise AccessDenied(...)
440: 
441:     def sql_filter_for(self, ctx):
442:         rule = self.resolve_rule(ctx.model_class, ctx.action)
443:         return rule.sql_filter(ctx)
444: ```
445: 
446: Then in `routes_fastapi.py`:
447: 
448: ```python
449: _resolver = OverrideResolver(DefaultResolver(), db_override_store)
450: ```
