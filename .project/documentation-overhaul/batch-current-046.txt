278: ## Gotchas
279: 
280: - **Import ordering is mandatory.** `n3tx_ui` must be imported before any
281:   model with `__ui__` or `__viewable__` is defined. If a model is defined
282:   first, `register_mixin()` hasn't run yet and the mixin is never injected.
283:   The model will lack `ViewableMixin` in its MRO and `schema['ui']` will
284:   be absent. No error is raised — the flag is silently ignored.
285: 
286: - **`__ui__` without `n3tx_ui` import = no schema `ui` key.** If you define
287:   `__ui__` but forget to import `n3tx_ui`, the class attribute exists but
288:   ViewableMixin is never injected and the `viewable` stage is never registered.
289:   `Product.schema()` will not contain a `'ui'` key.
290: 
291: - **Schema cache.** `schema['ui']` is only generated on the first `schema()`
292:   call. If `n3tx_ui` is imported after the first call, call
293:   `cls.invalidate_schema_cache()` to regenerate.
294: 
295: - **`__ui__` on a non-model class.** Only `ProtoModel` subclasses go through
296:   `__init_subclass__`. Plain Python classes with `__ui__` are unaffected.

1: # Widget System
2: 
3: > Part of [n3tx-ui](../README.md)
4: 
5: ## What This Covers
6: 
7: The widget base class, registry, built-in widgets, and extension API. Covers how `ui.widget` schema hints flow from Python model definitions to specialized frontend renderers.
8: 
9: ## Architecture
10: 
11: ```
12: Python model field
13:   Field(json_schema_extra={'ui': {'widget': 'currency', 'config': {'symbol': '$'}}})
14:       |
15:       v
16: Backend schema pipeline (widget stage)
17:   Injects ui.widget + ui.config into JSON Schema properties
18:       |
19:       v
20: Frontend: form.js getInput() / ntx-item.js sm()
21:   Calls getWidgetForField(fieldSchema)
22:       |
23:       v
24: registry.js: _widgets[name] lookup
25:   Returns { widget: WidgetInstance, config: ui.config }
26:       |
27:       v
28: Widget method call (context-dependent):
29:   display(value, config, schema) -> DOM Node     (detail views)
30:   edit(value, config, schema, onChange) -> DOM Node (form inputs)
31:   list(value, config, schema) -> string           (table cells, sm fields)
32:   validate(value, config, schema) -> string|null  (form validation)
33: ```
34: 
35: If no widget is registered for the field's `ui.widget` name, `getWidgetForField()` returns `{widget: null, config: {}}` and Formidable falls through to type-based rendering.
36: 
37: ## Interface
38: 
39: ### Widget base class
40: 
41: ```javascript
42: class Widget {
43:     // Render for detail/display context. Returns DOM Node.
44:     display(value, config, schema) { return document.createTextNode(value ?? ''); }
45: 
46:     // Render for edit context. Returns DOM Node (input element).
47:     edit(value, config, schema, onChange) { /* returns <input> */ }
48: 
49:     // Render for list/table cell. Returns plain text or HTML string.
50:     list(value, config, schema) { return String(value ?? ''); }
51: 
52:     // Validate value. Returns error message string or null.
53:     validate(value, config, schema) { return null; }
54: 
55:     // Utilities (inherited by all widgets)
56:     truncate(str, maxLen = 80)           // Ellipsis truncation
57:     escape(html)                         // HTML entity escaping
58:     el(tag, attrs = {}, children = [])   // DOM element builder
59: }
60: ```
61: 
62: ### Registry API
63: 
64: ```javascript
65: registerWidget(name, widgetInstance)    // Register by name (matches ui.widget)
66: getWidgetForField(fieldSchema)         // Returns { widget: Widget|null, config: Object }
67: hasWidget(name)                        // Check if registered
68: ```
69:

160: ## Gotchas
161: 
162: - **display() and edit() return DOM Nodes, list() returns a string.** This asymmetry exists because display/edit results are wrapped in container divs by Formidable (via `.outerHTML`), while list() output is inserted directly into HTML template strings by NTTItem's sm() method.
163: 
164: - **Widget dispatch requires both conditions.** `getWidgetForField()` returns a widget only if the name exists in the registry. But the callers in form.js and ntx-item.js additionally check `def.ui?.widget` before using the widget. This means registering a widget alone does not activate it -- the schema must also carry the `ui.widget` hint.
165: 
166: - **edit() must produce an element with data-key.** Formidable stamps `data-key` and `data-type` on the editable element (or the first input/textarea/select inside the returned node). This is required for `handleInputChange()` in NTTItem to process the value correctly. If your widget returns a complex DOM tree, ensure the primary input has these attributes or Formidable will stamp them on the outermost element.
167: 
168: - **Vendor libraries are optional.** MarkdownWidget checks `typeof marked !== 'undefined'` and falls back to `<pre>`. ConsoleWidget checks `typeof AnsiUp !== 'undefined'` and falls back to plain text. Include `vendor/marked.min.js` and `vendor/ansi_up.min.js` via script tags if you need these features.
169: 
170: - **The `el()` helper handles `on*` attributes as event listeners.** `this.el('button', {onclick: handler})` calls `addEventListener('click', handler)`, not `setAttribute('onclick', ...)`. Use this for interactive widget elements.

186: ## 🔮 Schema-Driven Development
187: 
188: This is where N3TX gets fun. A single model class encodes your entire application concern -- structure, behavior, permissions, and UI:
189: 
190: ```python
191: class Product(ProtoModel):
192:     __tablename__ = 'products'
193:     __storable__ = True
194:     __ui__ = {
195:         'field_order': ['name', 'price', 'description', 'comments', 'favorites'],
196:         'groups': {'main': ['name', 'description', 'price'], 'Social': ['comments', 'favorites']},
197:         'methods': {
198:             'comment': {'layout': 'inline', 'attach_to': 'comments'},
199:             'favorite': {'layout': 'button', 'icon': 'star', 'count_field': 'favorites'},
200:         },
201:         'renderer': {'item': 'ntx-item', 'list': 'ntx-list'},
202:     }
203:     __access__ = {
204:         'read': ANYONE, 'create': AUTHENTICATED,
205:         'update': OWNER | ROLE('admin'), 'delete': ROLE('admin'),
206:     }
207: 
208:     name: str = Field(min_length=1, max_length=200,
209:                       json_schema_extra={'ui': {'placeholder': 'Product name...'}})
210:     price: float = Field(gt=0,
211:                          json_schema_extra={'ui': {'widget': 'currency'},
212:                                             'access': {'view': 'anyone', 'edit': 'admin'}})
213:     description: str = Field(default='',
214:                              json_schema_extra={'ui': {'widget': 'textarea'}})
215:     comments: list[Comment] = Field(default=[])
216:     favorites: list[Like] = Field(default=[], description="Users who favorited this product")
217: 
218:     @expose_route('/comment', methods=['POST'])
219:     def comment(self, comment: Comment, user: User = None) -> str: ...
220: 
221:     @expose_route('/favorite', methods=['POST'], access=AUTHENTICATED)
222:     def favorite(self, user: User = None) -> str: ...
223: ```
224: 
225: From this definition, `ProtoModel.schema()` generates a JSON Schema carrying everything the frontend needs. You didn't write a single line of frontend code, and yet you've got forms, permissions, action buttons, and field grouping.
226: 
227: ### What gets generated automatically
228: 
229: | Concern | Generated from | How |
230: |---------|---------------|-----|
231: | CRUD API endpoints | `__tablename__`, model fields | Routes auto-registered |
232: | JSON Schema | Field types, validators, `json_schema_extra` | Pydantic generates it |
233: | DB table + migrations | `__storable__`, field annotations | SQLite auto-migrates |
234: | Relationship hydration | `list[T]` fields | Storage keeps local ids and hydrates objects on read |
235: | Access control (backend) | `__access__`, `@expose_route(access=...)` | Middleware enforces |
236: | Access control (frontend) | `access` in schema | UI hides/shows controls |
237: | Frontend entity classes | Schema properties, methods | DynamicClass created at runtime |
238: | Form rendering | `properties`, `ui.widget`, `ui.placeholder` | Form generator reads schema |
239: | Field ordering + grouping | `ui.field_order`, `ui.groups` | Fieldsets rendered automatically |
240: | Edit/delete button visibility | `access.update`, `access.delete` | Permissions checked from schema |
241: | Method action buttons | `schema.methods` | `<ntx-method>` renders them |
242: | Toggle endpoints | `@expose_route` + model method logic | Like/favorite over first-class models |
243: | Component tag resolution | `ui.renderer.item`, `ui.renderer.detail` | Router resolves on navigation |
244: 
245: ### The workflow
246: 
247: Your dev loop looks like this:
248: 
249: 1. Define or modify a Python model
250: 2. Restart the server
251: 3. Open the frontend -- it fetches the schema, creates entity classes, renders everything
252: 4. No frontend code changed. No routes added. No forms built. No permissions wired.
253: 
254: That's it. Change the model, see it everywhere.
