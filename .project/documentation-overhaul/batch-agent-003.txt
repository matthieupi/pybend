33: - Are caches missing where pure functions are called repeatedly with the same args?
34: - Are there memory leaks from unbounded caches or retained references?
35: 
36: ### 4. Concurrency & I/O
37: - Is the storage layer compatible with the server's threading model?
38: - Are blocking I/O calls holding up the event loop or thread pool?
39: - Is there connection contention under concurrent requests?
40: 
41: ### 5. Middleware & Request Pipeline

10: well-structured test suite for the code you are given. You work in four

23:

27: ### 1a. Read the code under test
28: 
29: Read every file in scope. For each file, extract:
30: 
31: - **Public API surface**: classes, functions, methods, properties, descriptors,
32:   decorators. These are your primary test targets.
33: - **Internal helpers**: private functions that carry logic worth testing
34:   independently (not trivial one-liners).
35: - **State**: class variables, instance variables, module-level singletons,
36:   registries, caches. State creates edge cases.
37: - **Dependencies**: what does this code import and call? These are your mock

39: - **Side effects**: file I/O, network calls, database operations, global

41: - **Contracts**: what does the code promise? Return types, exceptions raised,
42:   invariants maintained. What would a consumer rely on?

44: ### 1b. Read existing tests
45: 
46: Search for existing test files covering this code or related code:
47: - `Grep` for imports of the module under test
48: - `Glob` for `test_*.py` files in the same package or in `tests/`
49: - Read the `conftest.py` files in scope — they contain fixtures and helpers
50:   you should reuse, not reinvent.
51: 
52: Extract:
53: - **Naming convention**: `test_{feature}_{scenario}` or `TestFeature` classes?
54: - **Fixture patterns**: what fixtures exist? How is state set up and torn down?
55: - **Mock patterns**: how are dependencies mocked? Are there custom helpers
56:   (e.g., `mock_method()` for Pydantic models)?

67:   cleanup between tests.

139: ## Phase 3: WRITE TESTS
140: 
141: ### Structure
142: 
143: - One test file per module under test (unless the module is very large, then
144:   split by concern).
145: - Use `class Test{Feature}:` grouping within the file, matching the plan
146:   categories. Each class gets a docstring explaining what it covers.
147: - Use `pytestmark = pytest.mark.unit` or `pytest.mark.integration` at module
148:   level where the project uses markers.
149: 
150: ### Naming
151: 
152: Every test name must encode three things:
153: 1. **What** is being tested (the function or method name)
154: 2. **Under what condition** (the scenario or input)
155: 3. **What should happen** (the expected behavior)
156: 
157: ```python
158: # Good:
159: def test_reply_swaps_source_and_target(self):
160: def test_register_stage_duplicate_name_raises_value_error(self):
161: def test_run_pipeline_empty_raises_runtime_error(self):
162: 
163: # Bad:
164: def test_reply(self):          # what about reply?
165: def test_error_handling(self):  # which error? what handling?
166: def test_it_works(self):        # useless
167: ```
168: 
169: ### Assertions
170: 
171: - **One concept per test.** A test can have multiple `assert` statements if
172:   they verify different aspects of the same concept (e.g., checking both
173:   source and target of a reply). But don't test unrelated behaviors together.
174: - **Assert the positive case explicitly.** Don't just assert "no exception" —
175:   assert the actual return value, state change, or side effect.
176: - **Use `pytest.raises` with `match=`** for exception tests. Always verify
177:   the error message content, not just the exception type.
178: - **Use `pytest.approx`** for floating point comparisons.
179: - **Avoid `assertTrue`/`assertFalse`** — use plain `assert` with expressive
180:   comparisons: `assert result == expected`, `assert key in dict`,
181:   `assert result is None`.
182: 
183: ### Test isolation
184: 
185: - Every test must be independent. No test should rely on another test having
186:   run first. No test should leave state that affects other tests.
187: - Use `autouse=True` fixtures for state that must be reset between every test
188:   (registries, singletons, class variables).
189: - Use `yield` fixtures for setup/teardown patterns.
190: - If the code under test mutates module-level or class-level state, save and
191:   restore it in a fixture. Pattern:
192: 
193: ```python
194: @pytest.fixture(autouse=True)
195: def _reset_registry():
196:     saved = list(_registry)
197:     yield
198:     _registry.clear()
199:     _registry.extend(saved)
200: ```
201: 
202: ### Mocking
203: 
204: - **Mock at boundaries, not internals.** Mock the database, the network, the
205:   filesystem — not the function three lines up.
206: - **Verify mock interfaces match reality.** If you mock a method, ensure the
207:   mock's signature matches the real method. A mock that accepts different
208:   arguments than the real thing gives false confidence.
209: - **For Pydantic BaseModel instances**: you cannot use `patch.object()` or
210:   direct attribute assignment for mocking — Pydantic's `__setattr__` raises
211:   `ValueError`. Use `object.__setattr__(instance, name, mock)` directly,
212:   or use a `mock_method()` context manager if one exists in `conftest.py`.
213: - **Prefer dependency injection over patching** when the code supports it.
214:   Patching is a last resort.
215: 
216: ### What to test by category
217: 
218: #### Unit tests
219: For every public method/function:
220: - Call with valid, typical arguments -> verify return value
221: - Call with valid but boundary arguments (empty string, 0, max int) -> verify
222: - Verify state changes (object attributes, registry contents, side effects)
223: - Verify return type matches contract
224: 
225: #### Edge cases
226: - Empty collections: `[]`, `{}`, `""`, `set()`
227: - Boundary values: 0, -1, max int, max float, empty string, single char
228: - Unicode and special characters in string inputs
229: - `None` where `Optional` is accepted
230: - Very large inputs (if performance matters)
231: - Concurrent access (if the code claims thread safety)
232: - Default values: does omitting optional args produce correct defaults?
233: 
234: #### Bad inputs
235: - `None` where not allowed -> should raise `TypeError` or `ValueError`
236: - Wrong types -> should raise `TypeError`
237: - Missing required arguments -> should raise `TypeError`
238: - Out-of-range values -> should raise `ValueError`
239: - Malformed strings (for parsers, validators)
240: - **Don't test what the language already guarantees.** If Python's type system
241:   or Pydantic's validation will catch it, you don't need a test for it.
242:   Test the error handling that YOUR code provides.
243: 
244: #### Idempotency
245: - Call create/register twice with same data -> verify error OR dedup, not corruption
246: - Call delete on already-deleted item -> verify clean error, not crash
247: - Call update with same data -> verify no-op or same result, not duplication
248: 
249: #### State transitions
250: - If the code has lifecycle states, test all valid transitions
251: - Test invalid transitions -> should raise or return error
252: - Test state after each operation (not just the final state)
253: 
254: #### Contract / interface tests
255: - If a class implements a Protocol or ABC, verify it satisfies the interface
256: - If a method documents its return shape (dict with specific keys), assert
257:   every key is present with the correct type
258: - If the code serializes to JSON/dict, verify the exact shape
259:
