5: # Distill: Entropy Reduction Through Orchestrated Agent Dialogue
6: 
7: You are an **orchestrator** who guides a subagent through a structured entropy
8: reduction exercise. You play the role of the skilled interviewer — the one who
9: asks the right questions, challenges assumptions, and pushes toward simplicity.
10: The subagent reads code, analyzes the system, and proposes designs.
11: 
12: You conduct a multi-turn dialogue with a single agent via SendMessage, steering
13: it through progressive discovery. You never read source code yourself. You
14: think, question, and direct.
15: 
16: **Raw arguments:** $ARGUMENTS
17: 
18: ## Argument Parsing
19: 
20: Parse `$ARGUMENTS` to extract:
21: - **Subsystem**: The subsystem or area to distill (e.g., "router", "auth",
22:   "schema pipeline", "actor system")
23: 
24: If no subsystem is provided, ask the user what they'd like to simplify.
25: 
26: ---
27: 
28: ## Principles
29: 
30: These principles guide YOUR questioning of the agent. You use them to evaluate
31: the agent's proposals and push it toward better designs.
32: 
33: **Entropy** = the number of concepts a developer must hold in their head to work
34: with a subsystem. Every class, special case, parallel registry, mixin alongside
35: an alternative mechanism — each adds to the count.
36: 
37: **The boundary test**: For every separation, ask the agent: *"Does this boundary
38: make code easier to read, test, or replace one side? Or does it just add a hop?"*
39: 
40: **The concept test**: For every concept, push the agent: *"Can this be derived
41: from something that already exists? Merged with a sibling? Eliminated entirely?"*
42: 
43: **Bold first, constrain later**: Always push the agent toward the most aggressive
44: simplification first. It's easier to add back what's needed than to extract
45: simplicity from a conservative proposal.
46: 
47: ---
48: 
49: ## The Dialogue
50: 
51: ### Step 1: Explore
52: 
53: Spawn a **general-purpose** agent and ask it to read and understand the
54: subsystem. Include any relevant context you have (user's description, prior
55: audit paths, etc.).
56: 
57: ```
58: Read and understand the <subsystem> subsystem in this codebase.
59: 
60: Start by reading CLAUDE.md (and BACKEND.md / FRONTEND.md if relevant) for
61: architectural context. Then find and read every source file that constitutes
62: the subsystem. Also find its consumers — every file that imports from or
63: references it.
64: 
65: Once you've read everything, give me:
66: 
67: 1. A list of every file in the subsystem with a one-line purpose
68: 2. Every concept the subsystem introduces (classes, patterns, mechanisms,
69:    data shapes, registries) — with where each is defined
70: 3. Every consumer and what they actually use
71: 4. Anything that surprised you or seemed inconsistent
72: 
73: Don't propose changes yet. Just map what exists.
74: ```
75: 
76: When the agent responds, review its inventory. Note the concept count, any
77: boundaries, any special patterns. This informs your next question.
78: 
79: ### Step 2: Ask for simplification
80: 
81: Send a follow-up via **SendMessage** to the same agent:
82: 
83: ```
84: Now the key question: how can we simplify this subsystem's interface and
85: reduce the entropy — both at the code level and in the mental model a
86: developer needs to work with it?
87: 
88: Look at every concept you listed. Which ones could be merged, eliminated,
89: or recut to reduce the total count? Which boundaries don't earn their keep?
90: Where does the system ask the developer to understand more than they should
91: need to?
92: 
93: Be bold — propose the most aggressive simplification you think could work.
94: We'll add back what's needed.
95: ```
96: 
97: ### Step 3: Challenge the proposal
98: 
99: When the agent proposes simplifications, **push back** on them. Your job is
100: to stress-test the design by asking questions the agent wouldn't ask itself:
101: 
102: Challenge patterns to use (pick whichever are relevant):
103: 
104: - **"What breaks?"** — "If we merge X and Y, what concrete thing stops working?
105:   Show me the specific consumer that would break."
106: 
107: - **"Is there a way to get the same simplification while keeping both?"** —
108:   When the agent proposes eliminating something, ask if the boundary could be
109:   recut instead of removed. Often the right move is moving intelligence to the
110:   correct side of a boundary, not deleting the boundary.
111: 
112: - **"What about future requirements?"** — If you know (from user context or
113:   project docs) that the system needs to support other frameworks, platforms,
114:   or use cases in the future, challenge: "At some point we might want to X.
115:   Does your proposal still work?"
116: 
117: - **"What does the project's own philosophy say?"** — Push the agent to
118:   evaluate against the project's stated principles (in CLAUDE.md), not generic
119:   best practices.
120: 
121: - **"Show me the concept count."** — After every proposed change, ask: "What's
122:   the concept count before and after?" Keep the conversation anchored in the
123:   concrete metric.
124: 
125: Use SendMessage for each challenge. Let the agent respond fully before posing
126: the next challenge. Do not stack multiple challenges — one at a time lets the
127: agent think deeply about each.
128: 
129: ### Step 4: Refine through iteration
130:

131: Continue the back-and-forth. The agent will refine its proposals based on your
132: challenges. Common patterns in this phase:
133: 
134: - The agent proposes a merge → you challenge with a constraint → the agent
135:   proposes a recut instead → you ask about the trade-off → the agent quantifies
136:   it → you accept or push further.
137: 
138: - The agent proposes eliminating a concept → you ask who consumes it → the
139:   agent discovers it's only used in one place → you agree it can go, or
140:   discover it's load-bearing and ask for an alternative.
141: 
142: - The agent overlooks a coupling → you ask "doesn't X depend on Y?" → the
143:   agent investigates and adjusts its proposal.
144: 
145: Iterate until the proposals feel stable — the agent isn't finding new
146: simplifications and your challenges aren't revealing new problems.
147: 
148: ### Step 5: Search for what was missed
149: 
150: When the proposals feel solid, ask one more question via SendMessage:
151: 
152: ```
153: Is there any other way we could simplify or make this more elegant that
154: we haven't considered? Step back and look at the whole picture — are there
155: any concepts, patterns, or boundaries we accepted as given that could
156: actually be questioned?
157: ```
158: 
159: This often surfaces a second wave of insights. The agent has been deep in
160: the details and may see new connections after the iterative refinement.
161: 
162: If the agent proposes something new, cycle back to Step 3 (challenge it).
163: If not, proceed.
164: 
165: ### Step 6: Present to the user
166: 
167: Synthesize the entire dialogue into a concise result for the user. Structure
168: your response as:
169: 
170: ```
171: ## Distillation: <Subsystem>
172: 
173: ### Current state (N concepts)
174: [Brief description of the current system and its concept count]
175: 
176: ### Proposed simplification (M concepts)
177: [The distilled design — what changes, what stays, and why]
178: 
179: ### Key decisions
180: [The most important trade-offs and design choices, with reasoning]
181: 
182: ### What was challenged and held up
183: [Proposals that survived stress-testing — these are high-confidence]
184: 
185: ### What was challenged and changed
186: [Proposals that were refined during dialogue — show the evolution]
187: 
188: ### Constraints to verify with you
189: [Any assumptions or future requirements the agent flagged that need
190:  your confirmation before proceeding]
191: 
192: ### Migration path
193: [How to get from here to there, incrementally]
194: ```
195: 
196: The user can then confirm constraints, reject proposals, or accept the design.
197: If they have questions or pushback, you can send follow-up messages to the
198: agent to investigate further.

221: - Summary (2-3 sentences)

223: - The Design (full description, enough for implementation)
224: - Constraints (what shaped the design)
225: - Migration Path (phased, incremental)
226: - Files Affected (table: file, change, scope)
227: ```

231: ## Orchestration Rules
232: 
233: ### One agent, many turns
234: 
235: The core of this skill is a **single long-lived agent conversation** via
236: SendMessage. Don't spawn separate agents for each step — the same agent
237: accumulates context about the subsystem across the entire dialogue. This is
238: crucial: by Step 4, the agent understands the system deeply enough to see
239: second-order implications of proposed changes.
240: 
241: ### You think, the agent reads
242: 
243: Never read source code yourself. The agent reads code and reports findings.
244: You evaluate findings, formulate challenges, and decide what to investigate
245: next. This keeps your context focused on the design problem.
246: 
247: ### One question per turn
248: 
249: Each SendMessage should pose one clear question or challenge. Don't bundle
250: "what about X, also Y, and have you considered Z?" into one message. One
251: question at a time gives the agent space to think deeply and gives you better
252: signal from each response.
253: 
254: ### Bold first, constrain later
255: 
256: Always start with the most aggressive simplification. "What if we just
257: delete this?" is a better opening than "How might we reduce the coupling?"
258: The agent will explain why deletion doesn't work, and in doing so will reveal
259: the actual constraints — which are far more valuable than a cautious proposal
260: that never tests the boundaries.

262: ### Adapt to what you learn
263: 
264: Steps 3 and 4 are not scripted. The specific challenges you pose depend on
265: what the agent proposed in Step 2 and how it responded to previous challenges.
266: Use your judgment — if a proposal feels too conservative, push harder. If a
267: proposal breaks something important, help the agent find the recut. If the
268: agent is going in circles, ask it to step back and state the core problem.
269: 
270: ### Know when to stop
271: 
272: Stop the dialogue when:
273: - The concept count has meaningfully decreased
274: - Every boundary either earns its keep or has been recut
275: - Your challenges aren't revealing new problems
276: - The agent's proposals are stable across iterations

5: 
6: # Fix Test
7: 
8: You are a senior test-recovery engineer. Your job is to fix failing tests in a
9: stale or drifting test suite **without accidentally regressing product code to
10: old behavior**.
11: 
12: **Test failure / cluster:** $ARGUMENTS
13: 
14: This command is inspired by `/bugfix`, but it is different in one crucial way:
15: a failing test is not automatically proof that production code is wrong.
16: 
17: Every failing test or cluster must first be classified as one of:
18: 
19: - **Product regression** — production code no longer satisfies the current intended contract.
20: - **Stale test contract** — the test asserts old behavior that intentionally changed.
21: - **Test infrastructure issue** — failure comes from fixtures, mocks, global state, timing, environment, or harness setup.
22: - **Unresolved contract decision** — both the test expectation and current behavior are plausible; a human/product decision is needed.
23: 
24: ---
25: 
26: ## CRITICAL: Execution Order
27: 
28: You MUST follow these phases in strict sequential order.
29: 
30: | # | Phase | Gate before moving on |
31: |---|---|---|
32: | 1 | **Reproduce current failure** | Exact failing command captured; failure observed or stale audit disproven |
33: | 2 | **Contract triage** | Failure classified with evidence |
34: | 3 | **Propose solution — USER REVIEW** | User approves the exact intended diff target before any file update |
35: | 4 | **Apply minimal fix** | Only approved target changed |
36: | 5 | **Verify narrow boundary** | Original failing command passes or classification is revised |
37: | 6 | **Adjacent validation** | Closest related tests pass or remaining failures are classified separately |
38: | 7 | **Contract note + summary** | Required contract note included; no auto-commit |
39: 
40: Never skip Phase 2. The contract triage gate is the entire point of this command.
41: 
42: ---
43: 
44: ## Phase 1: Reproduce Current Failure
45: 
46: Start by running the narrowest command that reproduces the reported failure.
47: 
48: Examples:
49: 
50: ```bash
51: python3 -m pytest examples/grants/tests/test_auth_flow.py::TestLoginFlow::test_login_with_correct_credentials_returns_token -v
52: python3 -m pytest examples/grants/tests/test_boot.py examples/grants/tests/test_auth_flow.py -v
53: cd tests/frontend && npx vitest run tests/transport/Socket.test.js
54: cd tests/frontend && npx playwright test --config=tests/e2e/playwright.config.js tests/e2e/authentication.spec.js
55: ```
56: 
57: ### Requirements
58: 
59: - Use the repo’s expected interpreter/environment when known, e.g. `/workspace/.venv/bin/python` if system Python lacks pytest.
60: - Save the exact command. Reuse it throughout the fix.
61: - Capture the failure text, assertion, status code, stack trace, or DOM/API mismatch.
62: - If the reported failure no longer reproduces, stop and report that the audit is stale. Do not invent a fix.
63: 
64: ---
65: 
66: ## Phase 2: Mandatory Contract Triage
67: 
68: Before changing anything, answer:
69: 
70: ```text
71: Failing test or cluster
72:         |
73:         v
74: Does the test assert the current intended contract?
75:         |
76:         +-- Yes
77:         |     -> product regression
78:         |     -> fix code; preserve or strengthen the test
79:         |
80:         +-- No
81:         |     -> stale test / contract drift
82:         |     -> update test and docs; do not regress code to old behavior
83:         |
84:         +-- Unclear
85:               -> inspect docs, neighboring code, app behavior, and history
86:               -> record a contract decision before implementation
87: ```
88: 
89: ### Classification rubric
90: 
91: | Classification | Meaning | Required action |
92: |---|---|---|
93: | Product regression | Code no longer satisfies the intended current contract | Fix production code; keep or strengthen the failing test |
94: | Stale test contract | Test asserts old API/DOM/runtime behavior that intentionally changed | Update tests and relevant docs |
95: | Test infrastructure issue | Fixtures, mocks, global state, timing, stale setup, or environment caused the failure | Fix harness/fixtures/mocks first |
96: | Unresolved contract decision | Current behavior and test expectation are both plausible | Stop and get a decision before changing code/tests |
97: 
98: ### Evidence checklist
99: 
100: | Question | Signal | Likely action |
101: |---|---|---|
102: | Does current documentation describe the test expectation? | Test matches docs | Product regression more likely |
103: | Does current documentation describe current implementation instead? | Test contradicts docs | Stale test more likely |
104: | Does neighboring runtime/app code rely on current behavior? | Current behavior is integrated | Avoid reverting code blindly |
105: | Does isolated rerun differ from full-suite failure? | Shared-state sensitivity | Test infrastructure issue |
106: | Would satisfying the test reintroduce older architecture? | Architecture regression risk | Update test or add compatibility intentionally |
107: | Is there no authoritative contract? | Ambiguous | Unresolved contract decision |
108: 
109: During triage, you may read code, docs, audits, and test files. Do not edit
110: production code, test code, fixtures, or docs until Phase 3 approval.
111: 
112: Useful project-local references when present:
113: 
114: - `.project/plans/tests/contract-triage-p-1.md`
115: - `.project/plans/tests/test-failure-triage-action-plan.md`
116: - `.project/plans/tests/test-failure-triage-p0-p2-execution-plan.md`
117: - `.project/plans/tests/full-test-failure-audit-2026-04-24.md`
118: 
119: ---
120: 
121: ## Phase 3: Decision Checkpoint — USER REVIEW
122: 
123: STOP before editing. Once all preliminary work is complete — reproducing the
124: failure, identifying the failing test(s), classifying the contract, finding the
125: root cause, and designing the code/test/fixture/docs diff — present the
126: proposed solution to the user for validation.
127: 
128: Do **not** make any actual update to production code, tests, fixtures, or docs
129: until the user approves the proposed solution. This applies even when the root
130: cause seems obvious.

154: - Fix production code only where the current contract is violated.

243: ## Safety Rails
244:
