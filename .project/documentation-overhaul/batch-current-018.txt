394: ### "Not found" on Custom Endpoint
395: 
396: 1. Check schema: `GET /{ModelName}` → Look in `methods` object
397: 2. Verify URL pattern matches method type (static/class/instance)
398: 3. See: [Custom Endpoints - URL Patterns](./API_CUSTOM_ENDPOINTS.md#endpoint-url-patterns)
399: 
400: ### "Missing field: X"
401: 
402: 1. Check schema for required fields: `GET /{ModelName}` → Look in `required` array
403: 2. Ensure all required fields are in request body
404: 3. See: [CRUD - Create Resource](./API_CRUD_ENDPOINTS.md#create-resource)
405: 
406: ### "Invalid field 'X': ..."
407: 
408: 1. Check field type in schema: `GET /{ModelName}` → Look in `properties.X.type`
409: 2. Ensure request value matches expected type
410: 3. See: [Overview - Data Types](./API_OVERVIEW.md#data-types)
411: 
412: ### Foreign Key Not Resolving
413: 
414: Remember: Foreign keys are stored as IDs, not full objects.
415: 
416: ```javascript
417: // Response contains ID
418: const comment = await fetch('/comments/1').then(r => r.json());
419: // { user: 1 } ← This is an ID, not a user object
420: 
421: // Fetch full object separately
422: const user = await fetch(`/users/${comment.user}`).then(r => r.json());

### docs/API_OVERVIEW.md (598 total lines)
1: # N3TX API Documentation
2: 
3: **Version**: 0.8.2
4: **Base URL**: `http://localhost:8000` (default, configurable)  
5: **Protocol**: REST over HTTP/HTTPS  
6: **Content-Type**: `application/json` for generated JSON APIs; optional file upload/download routes use multipart and binary responses.
7: 
8: ## Purpose
9: 
10: N3TX automatically generates a complete REST API from your Python model definitions. This documentation explains how to interact with the generated endpoints from a frontend perspective.
11: 
12: ## Routing Modes
13: 
14: N3TX supports two routing modes, selectable via the `routing` parameter:
15: 
16: ### Direct Routing (default)
17: 
18: ```python
19: app = create_app(models=[Product, User], storage="sqlite:///app.db")
20: # or explicitly:
21: app = create_app(models=[Product, User], storage="sqlite:///app.db", routing='direct')
22: ```
23: 
24: HTTP requests go directly to route handlers which call StorableMixin CRUD methods. This is the simplest mode — no actor system involvement in request processing.
25: 
26: ### Actor Routing (Level 3)
27: 
28: ```python
29: app = create_app(models=[Product, User], storage="sqlite:///app.db", routing='actor')
30: ```
31: 
32: HTTP requests are translated into TX messages routed through the Matrix actor system:
33: 
34: ```
35: HTTP Request → NetworkAPI adapter → TX → Matrix → ActorModel.handler_crud → StorableMixin
36: HTTP Response ← NetworkAPI adapter ← TX ← Matrix ← ActorModel.handler_crud ←
37: ```
38: 
39: Actor routing enables interceptors (e.g., authentication at the protocol boundary), lifecycle events, and uniform message-based architecture across all protocols (HTTP, MCP, ActivityPub).
40: 
41: Both modes produce identical API endpoints and response formats. The choice is transparent to API consumers.
42:

44: 
45: ## Key Concepts
46: 
47: ### Models & Resources
48: 
49: Each N3TX model becomes a REST resource with automatic CRUD endpoints. For example:
50: 
51: - `User` model -> `/users` endpoints
52: - `Product` model -> `/products` endpoints
53: - `Comment` model -> `/comments` endpoints
54: 
55: ### Automatic Endpoint Generation
56: 
57: For every model marked as `__storable__ = True`, N3TX generates:
58: 
59: 1. **Schema Endpoint** - Get the model's JSON schema
60: 2. **Create** - Create new resource
61: 3. **List** - Get all resources
62: 4. **Get** - Get single resource by ID
63: 5. **Update** - Update existing resource
64: 6. **Delete** - Delete resource
65: 
66: ### Response Metadata
67: 
68: All CRUD route handlers call `.model_response()`, which injects two metadata fields at the top of every response object:
69: 
70: - `$schema` - URL to the model's JSON Schema (e.g., `http://localhost:8000/User`)
71: - `$id` - canonical class-name URL to this specific resource instance (e.g., `http://localhost:8000/User/1`)
72: 
73: This makes every response self-describing, allowing clients to discover schema information directly from the payload.
74: 
75: ### Custom Endpoints
76: 
77: Models can expose additional endpoints using the `@expose_route` decorator. These appear as:
78: 
79: - Static methods -> `/{resource}{custom_path}`
80: - Class methods -> `/{resource}{custom_path}`
81: - Instance methods -> `/{resource}/{id}{custom_path}`
82: 
83: Optional packages can also register package-owned routes through model capability
84: hooks. For example, `n3tx-files` adds multipart/binary routes for `File` because
85: file bytes cannot be represented as normal JSON method payloads.
86: 
87: ### Optional File API (`n3tx-files`)
88: 
89: When an app registers `n3tx_files.File`, these routes are available in addition
90: to normal File metadata CRUD/schema routes:
91: 
92: | Operation | Method | Path | Body/Response |
93: |---|---|---|---|
94: | Upload bytes | POST | `/files/upload` | multipart form field `upload`; returns `File.model_response()` |
95: | Download bytes | GET | `/files/{id}/download` | binary stream |
96: | Download mirror | GET | `/File/{id}/download` | binary stream |
97: 
98: Downloads support `Range: bytes=start-end`. Successful range reads return
99: `206 Partial Content` and `Content-Range`.
100: 
101: `File.resolve(ref)` and typed method materialization accept the canonical
102: absolute File `$id`, for example `http://localhost:5000/File/1`.
103: 
104: ### Nested Resources (Many-to-Many)
105: 
106: When models have relationships, N3TX creates nested endpoints:
107: 
108: - Parent resource: `/products`
109: - Child resources: `/products/{parent_id}/comments`
110:

113: ## General API Conventions
114: 
115: ### Request Format
116: 
117: Most generated API requests use:
118: - **Content-Type**: `application/json`
119: - **Accept**: `application/json`
120: 
121: Exceptions:
122: - `POST /files/upload` uses `multipart/form-data` with a form field named
123:   `upload`.
124: - `GET /files/{id}/download` and `GET /File/{id}/download` return binary bytes,
125:   not JSON.
126: 
127: ### Response Format
128: 
129: All successful responses return JSON with `$schema` and `$id` metadata at the top, followed by the resource data:
130: 

### docs/API_OVERVIEW.md (598 total lines)
131: ```json
132: {
133:   "$schema": "http://localhost:8000/User",
134:   "$id": "http://localhost:8000/User/1",
135:   "id": 1,
136:   "name": "Alice Johnson",
137:   "email": "alice@example.com",
138:   "age": 28
139: }
140: ```
141: 
142: ### `$id` Migration Note
143: 
144: N3TX response identity is class-name based. A response fetched through either
145: `/users/1` or `/User/1` advertises:
146: 
147: ```json
148: {
149:   "$schema": "http://localhost:8000/User",
150:   "$id": "http://localhost:8000/User/1"
151: }
152: ```
153: 
154: Legacy table-name routes such as `/users/1` remain supported as compatibility
155: transport paths, but new clients should treat `$id` as the canonical entity URL.
156: Nested entities use parent-scoped class-name identity such as
157: `/Product/1/Comment/2`. N3TX does not emit `$href` or `links`; `$id` is the
158: single response identity.
159: 
160: All error responses return:
161: ```json
162: {
163:   "detail": [
164:     {
165:       "file": "path/to/file.py",
166:       "line": 42,
167:       "function": "function_name",
168:       "code": "source code line",
169:       "error": "Error message"
170:     }
171:   ]
172: }
173: ```
174: 
175: ### HTTP Methods Semantics
176: 
177: | Method | Purpose | Idempotent | Safe |
178: |--------|---------|------------|------|
179: | GET | Retrieve resource(s) | Yes | Yes |
180: | POST | Create resource or trigger action | No | No |
181: | PUT | Partially update a resource; omitted fields remain unchanged | Yes | No |
182: | DELETE | Remove resource | Yes | No |
183: 
184: ### Status Codes
185: 
186: | Code | Meaning | When Used |
187: |------|---------|-----------|
188: | 200 | OK | Successful GET, PUT, DELETE |
189: | 201 | Created | Successful POST (resource created) |
190: | 400 | Bad Request | Validation error, missing required fields |
191: | 404 | Not Found | Resource with given ID doesn't exist |
192: | 422 | Unprocessable Entity | Invalid field type or format |
193: | 500 | Internal Server Error | Unexpected server error |

199: ### Understanding Foreign Keys
200: 
201: When a model has a foreign key reference:
202: 
203: ```python
204: class Comment(ProtoModel):
205:     user: Ref[User]  # Foreign key to User
206: ```
207: 
208: **In Requests** - Send the ID as an integer:
209: ```json
210: {
211:   "text": "Great product!",
212:   "user": 1
213: }
214: ```
215: 
216: **In Responses** - Receive the ID as an integer, along with `$schema` and `$id` metadata:
217: ```json
218: {
219:   "$schema": "http://localhost:8000/Comment",
220:   "$id": "http://localhost:8000/Product/5/Comment/1",
221:   "id": 1,
222:   "text": "Great product!",
223:   "user": 1
224: }
225: ```
226: 
227: **To Get Full Object** - Make a separate request:
228: ```javascript
229: // First, get the comment
230: const comment = await fetch('/Comment/1').then(r => r.json());
231: 
232: // Then, get the full user object
233: const user = await fetch(`/users/${comment.user}`).then(r => r.json());
234: ```
235: 
236: ### Local Model Collections
237: 
238: When models have local owned collections, N3TX stores ordered child ids on the
239: parent and returns hydrated child objects in the parent response:
240: 
241: ```python
242: class Product(ProtoModel):
243:     comments: list[Comment] = Field(default=[])
244: ```
245: 
246: Example response:
247: 
248: ```json
249: {
250:   "$schema": "http://localhost:8000/Product",
251:   "$id": "http://localhost:8000/Product/5",
252:   "id": 5,
253:   "comments": [
254:     {
255:       "$schema": "http://localhost:8000/Comment",
256:       "$id": "http://localhost:8000/Comment/1",
257:       "id": 1,
258:       "text": "Great!",
259:       "user": "http://localhost:8000/User/1"
260:     }
