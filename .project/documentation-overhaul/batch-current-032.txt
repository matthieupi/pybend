288: ## Observable
289: 
290: **File:** `core/Observable.js`
291: 
292: A mixin that adds pub/sub reactivity to any Actor subclass. Applied via:
293: 
294: ```javascript
295: Actor.subclass(N3TX, Observable)  // N3TX instances get signal/observe/notify
296: ```
297: 
298: ### Applied Methods (on prototype)
299: 
300: | Method | Signature | Description |
301: |--------|-----------|-------------|
302: | `signal(callback?, wait?)` | `callback: fn, wait: bool` | Without args: fires all registered callbacks with `this`. With callback: registers it. If `wait=false` (default), calls it immediately. Returns unsubscribe function. |
303: | `observe(property, callback)` | `property: string, callback: fn` | Registers a callback for a named property. Returns unsubscribe function. |
304: | `notify(property, newValue, oldValue)` | | Fires all callbacks registered via `observe()` for the given property. |
305: 
306: ### Internal Storage
307: 
308: Uses instance properties (not private fields, since it's a mixin):
309: - `this.__signals` - `Set<Function>` for signal() callbacks
310: - `this.__observers` - `Map<string, Set<Function>>` for observe() callbacks
311: - `this._initObservable()` - lazy initializer, called by each method
312: 
313: ### Important: Instance vs. Static Observable
314: 
315: `Observable.apply(Base)` only adds methods to `Base.prototype` (instance-level). For DynClass, static-level Observable methods (`signal`, `observe`) are added **manually** inside `prototype()` because:
316: - DynClass needs to be observable at the **class** level (components subscribe to the class itself)
317: - `Observable.apply` doesn't handle static properties

322: 
323: **File:** `core/N3TX.js` (within the same module)
324: 
325: Base class for data actors. Extends Actor with an `href` (remote endpoint URL) and a watcher notification pattern.
326:

328:

330: |----------|------|-------------|

334: ### Instance Methods
335: 
336: | Method | Signature | Description |
337: |--------|-----------|-------------|
338: | `watch(addr, immediate?)` | `addr: string, immediate: bool=true` | Adds `addr` to watchers. If `immediate` and `this.value` exists, sends UPDATE to the watcher immediately. |
339: | `notify(value?)` | `value: any` | Sends UPDATE TX to all watchers. If value is provided, sends it directly. Otherwise maps `this.value` children to their addresses. |

351: ## N3TX (Named Transfer Type)
352: 
353: **File:** `core/N3TX.js`
354: 
355: N3TX serves a **dual role**: it is both the **type registry** (static level) and the **entity base class** (instance level). After the PTT merge, N3TX absorbed all of PTT's registry and routing responsibilities.
356: 
357: ### Static Level: Type Registry
358: 
359: The static side of N3TX manages DynClass registration, the null-pointer bootstrap, and the universal ATTACH router.
360: 
361: #### Static State
362: 
363: | Property | Type | Description |
364: |----------|------|-------------|
365: | `N3TX.#prototypes` | `Map<string, DynClass\|null>` | Registry of all DynClass types. Three states per key: `undefined` (never seen), `null` (schema in flight), `DynClass` (ready). |
366: | `N3TX.#waiting` | `Map<string, Array>` | Queued TXs and attach callbacks for models whose schema is still in flight. |
367: 
368: #### Static Methods
369: 
370: | Method | Description |
371: |--------|-------------|
372: | `N3TX.has(addr)` | Checks if a DynClass is registered for the given model name. |
373: | `N3TX.get(addr)` | **Dual lookup:** `N3TX.get("Product")` returns DynClass. `N3TX.get("Product/1")` returns N3TX instance. |
374: | `N3TX.attach(addr, callback)` | Imperative attach with callback. If DynClass exists, fires immediately via `signal()`. If `null` (in flight), queues callback. If `undefined` (never seen), bootstraps schema fetch and queues. |
375: | `N3TX.ATTACH(data, tx)` | **Universal ATTACH router.** Handles both type-level (`"Product"`) and instance-level (`"Product/1"`) ATTACHes. Routes to DynClass if ready, queues if in flight, bootstraps if never seen. |
376: | `N3TX.SCHEMA(data, tx)` | **Bootstrap completion handler.** Receives schema from backend, creates DynClass via `prototype()`, stores in `#prototypes`, replays queued messages, triggers initial READ. Also registers `$defs` nested schemas as additional DynClasses. |
377: | `N3TX.#replayWaiting(addr, DynClass)` | Internal: replays queued TXs and attach callbacks for a model once its DynClass is ready. |
378: 
379: #### Null Pointer Bootstrap
380: 
381: The three-state pattern in `#prototypes` prevents duplicate schema fetches:
382: 
383: ```
384: N3TX.#prototypes.get("Product"):
385:   undefined  → Never seen → Set null, fetch schema, queue TX
386:   null       → Schema in flight → Queue TX (will replay when DynClass arrives)
387:   DynClass   → Ready → Forward TX directly to DynClass
388: ```
389: 
390: This replaces the old PTT lifecycle where a PTT instance existed in a half-initialized state before its schema arrived.

435: ## DynamicClass (DynClass)
436: 
437: **File:** `core/N3TX.js` (`prototype()` function)
438: 
439: When `N3TX.SCHEMA()` receives a model's schema from the backend, it calls `prototype(addr, schema, href)` to generate a runtime N3TX subclass. The DynClass **is** the type: it holds the schema, manages instances, handles CRUD, and provides Observable reactivity at the class level.
440: 
441: DynClasses are **born complete** — they never exist in a half-initialized state. The `prototype()` function returns a fully wired class with schema properties, methods, static CRUD handlers, and Actor/Observable integration.
442: 
443: ### `prototype(addr, schema, href)` — What It Does
444: 
445: ```javascript
446: function prototype(addr, schema, href) {
447:   // 1. Create DynClass extending N3TX
448:   const DynamicClass = class extends N3TX { ... }
449: 
450:   // 2. Set class name to addr (e.g., "Product")
451:   // 3. Store static _schema reference
452:   // 4. Initialize static state (_watchers, _pendingAttaches, __signals, __observers)
453: 
454:   // 5. For each schema property, define getter/setter on prototype:
455:   //    - getter: returns this.value[field]
456:   //    - setter: validates type, validates readOnly, updates value, calls notify()
457:   //    - Stores field labels for UI
458: 
459:   // 6. For each schema method, define prototype method:
460:   //    - Validates required parameters
461:   //    - Validates $ref parameter types
462:   //    - Calls this.call(method, args) for remote invocation
463: 
464:   // 7. Add static type-level methods (call, signal, observe, ATTACH, READ, UPDATE)
465:   // 8. Apply Actor.subclass(DynamicClass, Observable)
466: 
467:   return DynamicClass;
468: }
469: ```

485: ### Static Methods
486: 
487: | Method | Description |
488: |--------|-------------|
489: | `DynClass.call(method, data?, meta?)` | Sends a TX from the DynClass (type-level). **Omits `source`** so that `Actor._send` assigns it to `className` during Case 3 bubble — this avoids double-prefixing like `"Product/Product"`. |

496: ### Two Queues
497: 
498: DynClass uses a second queue (`_pendingAttaches`) that is separate from `N3TX.#waiting`:
499: 
500: | Queue | Location | Purpose |
501: |-------|----------|---------|
502: | `N3TX.#waiting` | N3TX static | TXs waiting for DynClass to be **created** (schema not yet received) |
503: | `DynClass._pendingAttaches` | DynClass static | Instance ATTACHes waiting for **READ to complete** (DynClass exists but instances not yet loaded) |

15: ## Overview
16: 
17: N3TX is a browser-side runtime for building schema-driven UIs on top of the N3TX backend. It uses an **Actor model** for all inter-component communication: every entity in the system (data models, UI components, the network layer) is an Actor with an address, an inbox, and a send method. Messages flow through a central **Matrix** (root actor) that routes locally or forwards to the network.
18: 
19: The key design goals:
20: - **Schema-driven**: The backend defines models (via Pydantic/OpenAPI). The frontend pulls those schemas at runtime and generates typed entity classes dynamically.
21: - **Decoupled**: UI components never call HTTP directly. They send messages to data actors, which handle remote calls transparently.
22: - **Hierarchical routing**: Actors form a tree. Messages route through the tree, bubbling to the Matrix when the target is not a local child.

59: ## Class Hierarchy
60: 
61: ```
62: Actor                          # Base actor: addr, inbox, send, children, spawn
63:   |
64:   +-- Matrix                   # Singleton root actor, message router + network gateway
65:   |
66:   +-- Router                   # Navigation state actor (route, history stack, URL sync, Observable)
67:   |
68:   +-- TT (Transfer Type)       # Actor with href (remote endpoint) + watcher/notify pattern
69:   |     |
70:   |     +-- N3TX                # Type registry (static) + entity base class (instance)
71:   |           |
72:   |           +-- [DynClass]   # Runtime-generated subclass per model (e.g. "Product")
73:   |                 |
74:   |                 +-- instances  # Per-entity N3TX instances (Product/1, Product/2, ...)
75:   |
76:   +-- Component (HTMLElement)  # Unified web component base (Actor + Shadow DOM + schema + adaptive display)
77:         |
78:         +-- NTTElement         # Single entity lifecycle (UPDATE, DESCRIBE, READ, save)
79:         |     |
80:         |     +-- NTTItem      # Built-in default: Formidable auto-render + edit toggle
81:         |
82:         +-- ListElement        # Collection lifecycle (subscribe, UPDATE, SELECT, childTag/template resolution)
83:         |     |
84:         |     +-- NTTList      # Built-in default: grid of children (19 lines)
85:         |
86:         +-- NTTRouter          # Generic view container ("mini browser"), controlled via Router
