6: Write a comprehensive handoff document that lets a fresh agent continue this session with minimal rediscovery.
7: 
8: The handoff is not just a summary. It is an engineering continuation packet: preserve the user's goal, the conversational context that shaped decisions, current repo state, implementation progress, verification evidence, unresolved risks, and the exact recommended next moves.
9: 
10: Save the handoff document to /workspace/.project/handoffs/. Use an explicit, 
11: timestamped filename such as `handoff-YYYYMMDD-HHMMSS.md`.
12: 
13: If command arguments were provided, treat them as the requested next-session focus and tailor the handoff toward that continuation path.
14: 
15: Next-session focus:
16: 
17: ```text
18: $ARGUMENTS

21: ## Writing style
22: 
23: Match this project's build/plan artifact style:
24: 
25: - ✅ Lead with outcomes and current state.
26: - 📍 Make scope, files, modules, routes, commands, and artifacts easy to scan.
27: - 🧵 Preserve relevant conversational context, including user intent, preferences, corrections, and approvals.
28: - 🗺️ Include ASCII diagrams when they clarify architecture, flow, ownership, sequencing, or handoff boundaries.
29: - 📊 Use compact tables for changed files, decisions, risks, verification, and next steps when they reduce prose.
30: - 💻 Include concise code snippets, command examples, route shapes, payload examples, or pseudo-diffs when they help the next agent act safely.
31: - 🧪 Separate verified facts from assumptions and gaps.
32: - ⚠️ Surface blockers, risks, compatibility issues, and places where the next agent must verify before editing.
33: - ✨ End with concrete next steps in priority order.
34: 
35: Be precise and implementation-grade. Avoid vague statements like "fix remaining issues" unless you name the files, functions, tests, routes, or symptoms involved.

7: # Start From Handoff
8: 
9: Resume from a prior engineering handoff with minimal rediscovery. Select the
10: requested handoff, read it fully, load the skills and context it names, inspect
11: the referenced docs/code, and report readiness before making any changes.

15: ## Selection behavior
16: 
17: Handoffs live under:
18: 
19: ```text
20: /workspace/.project/handoffs/
21: ```
22: 
23: Supported arguments:
24: 
25: ```text
26: /start-handoff        # latest handoff, same as -1
27: /start-handoff -1     # latest handoff
28: /start-handoff -2     # second latest handoff
29: /start-handoff -3     # third latest handoff
30: /start-handoff --list # list handoffs newest-first and stop
31: /start-handoff <text> # latest handoff, with <text> as continuation focus
32: ```
33: 
34: Use this Python selector rather than shell truncation commands:
35: 
36: ```bash
37: python - <<'PY'
38: from pathlib import Path
39: 
40: handoffs = sorted(
41:     Path('/workspace/.project/handoffs').glob('handoff-*.md'),
42:     key=lambda p: (p.stat().st_mtime, p.name),
43:     reverse=True,
44: )
45: 
46: for i, path in enumerate(handoffs, start=1):
47:     print(f'-{i} {path}')
48: PY
49: ```
50: 
51: Then choose the handoff as follows:
52: 
53: 1. If `$ARGUMENTS` is empty, select `-1`.
54: 2. If `$ARGUMENTS` is `--list`, list handoffs newest-first and stop.

56:    the Nth newest handoff.
57: 4. If `$ARGUMENTS` contains other text after the ordinal, preserve that text as
58:    the continuation focus.
59: 5. If `$ARGUMENTS` is text without an ordinal, select `-1` and treat the text
60:    as the continuation focus.
61: 6. If the selected ordinal does not exist, report the available handoffs and
62:    stop without guessing.

3: description: Improve codebase architecture by aligning it with N3TX patterns, primitives, architecture, intent, and philosophy. Use when the user wants N3TX-oriented architecture review, refactoring opportunities, framework-aligned simplification, or asks to improve N3TX alignment.
4: ---
5: 
6: # Improve N3TX Alignement
7: 
8: Explore a codebase through the lens of N3TX architecture, surface places where the implementation fights or bypasses the framework, and propose refactors that make the system more aligned with N3TX patterns, primitives, intent, and philosophy.
9: 
10: This skill is inspired by `improve-codebase-architecture`, but the improvement target is more specific: **make the codebase feel like an idiomatic N3TX system rather than an application that merely happens to run on top of N3TX**.
11: 
12: The goal of N3TX is to provide patterns and primitives that **simplify systems and improve maintainability**. Treat N3TX alignment as a simplification exercise first: prefer removing duplicated concepts, bespoke glue, local mini-frameworks, and accidental complexity over adding new layers. In most good N3TX refactors, the net result should be **less code, fewer concepts, and clearer ownership**.
13: 
14: ## North Star
15: 
16: Prefer architecture that is:
17: 
18: - **N3TX-native**: behavior is expressed through N3TX primitives instead of parallel custom mechanisms.
19: - **Declarative where possible**: intent is captured in stable definitions, metadata, schemas, routes, methods, resources, or framework-owned registration points.
20: - **Composable**: application behavior emerges from small N3TX-aligned parts rather than bespoke one-off flows.
21: - **Boundary-oriented**: modules expose intent and hide incidental mechanics.
22: - **Convention-friendly**: new code follows the framework's established file shapes, lifecycle, naming, and extension points.
23: - **Testable at the right boundary**: tests validate N3TX-visible behavior rather than internal glue.
24: - **Removal-first**: remove more than you add whenever possible; use N3TX primitives to collapse bespoke code paths.
25: - **Entropy-reducing**: refactors remove duplicate concepts, local mini-frameworks, and accidental divergence from N3TX's mental model.
26: 
27: ## Process
28: 
29: ### 1. Explore the codebase
30: 
31: Use the Agent tool with `subagent_type=explore` to navigate the codebase naturally. Do not follow rigid heuristics — explore organically and note where the system feels less N3TX-native than it could be.
32: 
33: Look for friction such as:
34: 
35: - Where does application code recreate behavior that N3TX already has a primitive for?
36: - Where are routes, methods, resources, schemas, forms, metadata, permissions, discovery, lifecycle hooks, or UI integration handled by ad hoc glue?
37: - Where does caller code need to know too much about framework internals or implementation details?
38: - Where do modules expose mechanics instead of N3TX-level intent?
39: - Where is configuration duplicated across Python, frontend assets, schemas, tests, or docs?
40: - Where are naming, registration, discovery, or lifecycle patterns inconsistent with nearby N3TX modules?
41: - Where do tests assert local implementation details instead of externally observable N3TX behavior?
42: - Where would a new contributor familiar with N3TX expect a concept to live somewhere else?
43: 
44: The friction you encounter is the signal. Treat repeated confusion, code bouncing, local conventions, and duplicated framework concepts as architectural evidence.
45: 
46: ### 2. Identify N3TX alignment candidates
47: 
48: Present a numbered list of improvement candidates. This section must be **fairly detailed**; it should be useful enough for the user to compare candidate refactor directions without needing to inspect the code immediately.
49: 
50: For each candidate, include:
51: 
52: 1. **Candidate title**: A concise name for the alignment opportunity.
53: 2. **Current shape**: The modules, files, concepts, and execution paths involved.
54: 3. **Observed friction**: What felt hard to understand, test, extend, or reason about.
55: 4. **N3TX misalignment**: Which N3TX pattern, primitive, architectural intent, or philosophy the current shape appears to fight, bypass, duplicate, or underuse.
56: 5. **Motive for change**: Why this matters now — maintainability, extensibility, correctness, testability, user experience, contributor onboarding, or framework coherence.
57: 6. **Improvement options**: Present 2-3 plausible directions, such as:
58:    - adopt an existing N3TX primitive directly
59:    - move behavior behind a N3TX-owned boundary
60:    - consolidate duplicated definitions into a single source of truth
61:    - replace imperative glue with declarative registration or metadata
62:    - introduce a thin adapter around non-N3TX concerns
63:    - deepen a module so callers speak in N3TX concepts
64:    - delete a custom abstraction because a N3TX primitive already expresses the intent
65: 7. **Recommended direction**: Choose the strongest option and explain why.
66: 8. **Why this is a good N3TX approach**: Explain how the recommendation improves alignment with N3TX's architecture, primitives, and philosophy.
67: 9. **Work overview**: Summarize the concrete work required to move in that direction:
68:    - files or modules likely to change
69:    - new or changed interfaces
70:    - migration sequence
71:    - tests to add, rewrite, or delete
72:    - documentation or examples to update
73:    - compatibility or rollout concerns
74: 10. **Expected outcome**: What becomes simpler, more declarative, more composable, or more framework-native after the change.
75: 11. **Risk / uncertainty**: Any unknowns that need confirmation before implementation.
76: 
77: When comparing options, strongly prefer the path that removes the most accidental complexity while preserving behavior. Adding a new abstraction is only a good N3TX alignment move when it lets the system delete more scattered logic, duplicated definitions, or caller knowledge elsewhere.
