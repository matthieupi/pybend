2: 
3: ## Philosophy
4: 
5: N3TX absorbs the data plumbing — storage, fetching, state, serialization — so developers focus on what makes their app unique. Define a model, get an API, a schema, a working UI.
6: 
7: **The model is the app.** A Python model definition is the single source of truth for the entire stack — data structure, validation, API endpoints, JSON Schema, access control, UI rendering. The framework derives everything else; if the schema can carry it, the developer shouldn't repeat it.
8: 
9: **Zero to working, then customize.** Everything works with no configuration. Customization is additive — override one piece without rebuilding the rest, at any level from auto-generated UI down to raw messages. The framework should never force a developer to understand the whole stack just to change one thing.
10: 
11: **Primitives, not opinions.** The framework provides composable building blocks — base classes, schema extensions, rendering utilities — not a rigid component library. Developers extend and compose; the framework owns the data lifecycle, developers own presentation and interaction.
12: 
13: **Backend is authoritative.** The backend defines models, schemas, access rules, relationships, and UI hints. The frontend reads these at runtime and adapts — deploying a new model or changing a field propagates to the UI automatically. The frontend never duplicates what the backend already knows.
14: 
15: **Transparent, not magical.** Nothing is hidden behind opaque abstractions. Actor messaging, schema resolution, DynamicClass creation — all inspectable, all overridable. The value is in not making you do it by hand, not in hiding it. A developer should trace any behavior from HTML tag to network request in under a minute.
16: 
17: **Modular where it simplifies, coupled where it must.** Real boundaries get enforced — the `authorize` package has zero N3TX imports, StorableMixin is injected not inherited, the Actor system knows nothing about HTML. But don't split genuinely single concerns for modularity's sake. The test: does this boundary make code easier to read, test, or replace one side? If it just adds a hop, keep it together.

105: ## Development Workflow
106: 
107: ### Before Making Changes
108: 
109: Before writing any code, review the area you are about to change. Understand the intent behind the existing implementation — why it was built this way, what patterns it follows, and how it fits into the larger system. Changes must be consistent with the architecture already in place. Do not work around the framework; work with it.
110: 
111: **Consistency is paramount.** N3TX's power comes from a small number of patterns applied uniformly across the entire stack. A single inconsistency — a hand-rolled route bypassing `register_routes()`, a frontend component fetching data outside the schema flow, a model that stores data differently from every other model — creates confusion, breaks assumptions, and compounds into real bugs over time. Every change should reinforce the existing architecture, not erode it. When in doubt, look at how the same thing is done elsewhere in the codebase and follow that pattern.
112: 
113: ### Bug Fixes
114: 
115: **Test-Driven Bug Fixing (TDD).** Every bug fix MUST follow the red-green-refactor cycle:
116: 
117: 1. **Red — Write a failing test first.** Before touching any production code, write a test that reproduces the reported bug. The test should fail for the same reason the bug manifests. This proves you understand the bug and gives you a clear signal when it's fixed. Place the test in the appropriate test directory (see [Tests](#tests) below).
118: 
119: 2. **Green — Fix the bug.** Make the minimal change needed to turn the failing test green. Do not refactor, do not clean up, do not fix adjacent issues — just make the test pass.
120: 
121: 3. **Refactor — Clean up if needed.** Once green, improve the fix if the code can be clearer or more consistent with surrounding patterns. The test ensures you don't regress.
122: 
123: If the bug cannot be reproduced with a test (e.g., environment-specific, timing-dependent), document why in a comment on the fix and describe the manual reproduction steps. But the default is always: **test first, fix second**.
124: 
125: Beyond standard analysis (reproduce, isolate, fix, verify), always ask **why** the bug exists. Most bugs are symptoms of deeper misalignment, not simple typos.
126: 
127: **Root cause categories:**
128: 
129: 1. **Misunderstood architecture.** The change works in isolation but conflicts with the system's actual patterns. Fix: understand the correct pattern, rewrite to be consistent. If the same area keeps producing bugs, improve its documentation.
130:

137: ## Architecture Overview
138: 
139: N3TX is a schema-driven framework where **model definitions are the single source of truth**. Models flow through: Model Definition → JSON Schema → API Routes → Frontend Rendering.
140: 
141: For full architecture details, read `/workspace/docs/ARCHITECTURE.md`.
142: 
143: ### Three Levels of Bootstrapping
144: 
145: ```python
146: # Level 1 — One-liner via create_app():
147: app = create_app(models=[Product, User], storage="sqlite:///app.db")
148: 
149: # Level 2 — Builder via N3TXApp:
150: pb = N3TXApp(storage="sqlite:///app.db")
151: pb.model(Product).model(User).join(Product, Comment)
152: app = pb.build()
153: 
154: # Level 3 — Raw primitives (full manual control):
155: register_model(Product, storage=storage_backend)
156: register_routes(registered_models)
157: ```
158: 
159: Level 3 with `routing='actor'` wires `NetworkAPI` adapter + `auth_interceptor` on `request` + routes via `create_api_routes()`. All three levels produce identical API endpoints and responses.
160: 
161: ### Backend (Python/FastAPI)
162: 
163: Models extend `ProtoModel` (or `ActorModel` for actor capabilities). `ProtoModel.schema()` orchestrates the schema pipeline, `model_response()` runs the dump pipeline. Models are registered via `register_model()` and routes auto-generated via `register_routes()`. See `BACKEND.md` for the full backend pipeline diagram and key files.
164: 
165: ### Frontend (Vanilla JS Web Components)
166: 
167: The frontend bootstraps by fetching schema from the backend. `N3TX.SCHEMA()` creates DynamicClasses via `prototype()`, which are then rendered by Web Components (`ntx-list`, `ntx-item`, `ntx-method`, `ntx-stream`) with forms generated by `Formidable`. See `FRONTEND.md` for the frontend architecture diagram and key files, and `packages/n3tx-ui/docs/styling.md` for the theme/token contract and frontend verification workflow.
168: 
169: ### Data Flow: Request Lifecycle
170: 
171: 1. Frontend `<ntx-list model="Product">` triggers schema fetch → `GET /Product`
172: 2. Backend returns JSON Schema with `$schema`, `$id`, `properties`, `$defs`, `methods`
173: 3. Frontend creates DynamicClass from schema, registers nested `$defs` models
174: 4. DynamicClass triggers `READ` → `GET /products?limit=20&offset=0` (paginated)
175: 5. Backend returns `{data: [...], meta: {total, limit, offset, has_more}}` with `$schema`/`$id` on each item
176: 6. Frontend creates instances, renders via `ntx-item` components with "Load More" button if `has_more`

178: ## Schema-Driven Development
179: 
180: Write a Python model, get a working full-stack application. The model definition is the only thing a developer writes. Everything else — API, validation, storage, UI, permissions, navigation — is derived from the schema that model produces. Any project can be transformed into a full stack application by turning a few classes into models.
181: 
182: For full details, read `/workspace/docs/CORE.md`.
183: 
184: ### Canonical Model Example
185: 
186: ```python
187: from n3tx_core.models.proto_model import ProtoModel
188: from n3tx_core.models.ref import ListRef
189: from n3tx_core.utils.decorators import expose_route
190: from n3tx_core.authorize import ANYONE, AUTHENTICATED, OWNER, ROLE
191: 
192: class Product(ProtoModel):
193:     __tablename__ = 'products'
194:     __storable__ = True
195:     __ui__ = {
196:         'field_order': ['name', 'price', 'description', 'comments'],
197:         'groups': {'main': ['name', 'description', 'price'], 'Social': ['comments']},
198:         'renderer': {'item': 'ntx-item', 'list': 'ntx-list'},
199:     }
200:     __access__ = {
201:         'read': ANYONE, 'create': AUTHENTICATED,
202:         'update': OWNER | ROLE('admin'), 'delete': ROLE('admin'),
203:     }
204: 
205:     name: str = Field(min_length=1, max_length=200,
206:                       json_schema_extra={'ui': {'placeholder': 'Product name...'}})
207:     price: float = Field(gt=0,
208:                          json_schema_extra={'ui': {'widget': 'currency'},
209:                                             'access': {'view': 'anyone', 'edit': 'admin'}})
210:     description: str = Field(default='',
211:                              json_schema_extra={'ui': {'widget': 'textarea'}})
212:     comments: ListRef[Comment] = Field(default=[])
213: 
214:     @expose_route('/comment', methods=['POST'])
215:     def comment(self, comment: Comment) -> str: ...
216: ```

218: ### What Gets Generated (zero code required)
219: 
220: | Concern | Generated from | Where it happens |
221: |---------|---------------|-----------------|
222: | CRUD API endpoints | `__tablename__`, model fields | `register_routes()` in `routes_fastapi.py` |
223: | JSON Schema | Field types, validators, `json_schema_extra` | `ProtoModel.schema()` via `proto_schema` pipeline |
224: | Enriched JSON responses | `model_response()`, dump pipeline stages | `proto_dump` pipeline (`base` → `relationships` → `schema_url` → `instance_url` → `populate` → extensions) |
225: | DB table + migrations | `__storable__`, field annotations | `StorableMixin` injection, `sqlite_migration.py` |
226: | JSON field storage | `dict`, `list`, `List[str]` etc. fields | `sqlite_storage.py` auto-serializes to/from JSON TEXT |
227: | FK hydration (href arrays) | `ListRef[T]` fields, `__fk_models__` | `sqlite_storage.py` on read |
228: | Access control | `__access__`, `@expose_route(access=...)` | `routes_fastapi.py` auth injection |
229: | Frontend entity classes | Schema properties, methods | `N3TX.SCHEMA()` → `prototype()` → DynamicClass |
230: | Form rendering | `properties`, `ui.widget`, `ui.placeholder` | `Formidable.getForm()` reads schema |
231: | Field order + grouping | `ui.field_order`, `ui.groups` | `form.js` renders fieldsets |
232: | Show/hide fields | `ui.display`, field-level `access` | `form.js` + `Permissions.js` |
233: | Protected fields | `__protected_fields__` | Route layer auto-injects on create, strips on update; `form.js` hides in edit mode |
234: | Edit/Delete button visibility | `access.update`/`access.delete` + OWNER check | `ntx-item.js` checks permissions |
235: | Pagination (list endpoints) | `?limit=N&offset=M` query params | `sqlite_storage.py` COUNT + LIMIT/OFFSET |
236: | Authenticated user injection | `user: User` param on `@expose_route` methods | `_resolve_user()` in `routes_fastapi.py` |
237: | Method buttons | `schema.methods` | `<ntx-method>` reads method signatures |
238: | Streaming SSE endpoints | `@expose_route(stream=True)` + async generator | `routes_fastapi.py` / `network_api.py` SSE handler |
239: | Streaming UI component | `schema.methods[m].stream` flag | `<ntx-stream>` reads method schema, renders progressive output |
240: | Stream event schemas | `@expose_route(events={...})` | `proto_model.py` serializes event ProtoModels into `methods[m].events` |
241: | Stream event dispatch | `NTTStreamAgent` + UPPERCASE handlers | `NTTStreamAgent` (extends `NTTStream`) dispatches to `this.TEXT()` etc. |

348: ## Cross-Cutting Patterns
349: 
350: ### Custom Methods
351: ```python
352: @expose_route('/like', methods=['POST'], access=AUTHENTICATED)
353: def like(self) -> str:
354:     ...
355: ```
356: Appears in schema under `methods`, frontend renders via `<ntx-method>` (or `<ntx-stream>` for streaming methods). The `access=` parameter controls authorization. The `stream=True` parameter marks the method as streaming.
357: 
358: ### Streaming Methods
359: Custom methods can stream progressive results via SSE or WebSocket:
360: 
361: ```python
362: @expose_route('/generate', methods=['POST'], stream=True, access=AUTHENTICATED)
363: async def generate(self):
364:     for i in range(5):
365:         await asyncio.sleep(0.1)
366:         yield {'chunk': f'Part {i}'}
367: ```
368: 
369: SSE wire format: `event: chunk|done|error`, `data: {json}`. Stream protocol uses `meta: {req, stream: true, seq: N}` for chunk correlation and `meta: {stream_end: true}` for termination.
370: 
371: #### Schema-Declared Stream Events
372: 
373: Streaming methods can declare their event vocabulary with `events=` on `@expose_route`. Event types are non-storable `ProtoModel` subclasses:
374: 
375: ```python
376: class TextChunk(ProtoModel):
377:     text: str = Field(default='')
378: 
379: @expose_route('/stream', methods=['POST'], stream=True,
380:               events={'text': TextChunk, 'done': DoneChunk})
381: async def stream_method(self, task: str):
382:     yield {'name': 'text', 'data': {'text': 'hello'}}
383: ```
384: 
385: Events appear in schema as `methods[m].events` with full JSON Schema per event type. See `docs/AGENTS.md` → Streaming for the complete pattern.
