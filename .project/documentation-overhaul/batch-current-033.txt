194: The primary data flow for rendering a list of entities:
195: 
196: ```
197: <ntx-list model="Product">
198:   |
199:   | attributeChangedCallback("model", "Product")
200:   | TX { ATTACH, source: list-addr, target: N3TX, data: "Product" }
201:   v
202: Matrix.inbox() -> routes to N3TX (static)
203:   |
204:   | N3TX.ATTACH() - "Product" not in #prototypes (undefined)
205:   | Sets #prototypes["Product"] = null (schema in flight)
206:   | Queues the ATTACH TX in #waiting
207:   | Dispatches: TX { SCHEMA, source: N3TX, target: http://...8000/Product, meta: {remote:true} }
208:   v
209: Matrix.inbox() -> target not local -> NetworkAdapter.send()
210:   |
211:   | HTTP.get("http://localhost:8000/Product") -> backend returns JSON schema
212:   v
213: NetworkAdapter.httpCallback() -> swaps source/target, sets name to SCHEMA
214:   | TX { SCHEMA, source: http://...8000/Product, target: N3TX, data: <schema> }
215:   v
216: Matrix.inbox() -> routes to N3TX (static)
217:   |
218:   | N3TX.SCHEMA(data):
219:   |   - Calls prototype(addr, schema, href) -> creates DynClass "Product"
220:   |   - Stores DynClass in #prototypes["Product"]
221:   |   - Registers any $defs models as additional DynClasses
222:   |   - Replays queued TXs from #waiting (the original ATTACH)
223:   |   - DynClass.call('READ', {}) triggers data fetch
224:   v
225: DynClass "Product" receives replayed ATTACH
226:   | DynClass.ATTACH() -> adds list as watcher
227:   |
228:   | Meanwhile, DynClass.call('READ') sends:
229:   | TX { READ, source: Product, target: http://...8000/products, meta: {remote:true} }
230:   v
231: NetworkAdapter -> HTTP.get(.../products) -> backend returns [{id:1,...}, ...]
232:   | httpCallback: name stays READ (no meta.inbox override here)
233:   | TX { READ, source: http://...8000/products, target: Product, data: [...] }
234:   v
235: DynClass.READ(data):
236:   | Creates N3TX instances for each record, stores in DynClass.instances
237:   | Replays any _pendingAttaches
238:   | Notifies all watchers (the list)
239:   | TX { UPDATE, source: Product, target: <list-addr>, data: ["Product/1","Product/2",...] }
240:   v

242:   | this.value = array of address strings
243:   | this.render() creates child elements via createChild(addr), sets el.ref = "Product/1"

250:   | DynClass.ATTACH() -> instance-level -> forwards to N3TX instance

368: ## Upcoming: Backend Actor Bridge
369: 
370: <a id="upcoming-backend-actor-bridge"></a>
371: 
372: The v0.8 backend introduces a Python-side Actor/Matrix/TX messaging system that mirrors the frontend's architecture. Backend actors communicate via the same TX message envelope (`name`, `source`, `target`, `data`, `meta`) and route through a backend Matrix.
373: 
374: **Wave 3 (planned):** A WebSocket bridge will connect frontend actors to backend actors, enabling bidirectional real-time messaging across the stack. The frontend `Socket.js` transport and the backend's Actor system will share a common TX protocol, allowing:
375: 
376: - Backend actors to push updates to frontend components without polling
377: - Frontend actors to send messages to specific backend actors by address
378: - Cross-stack actor hierarchies where backend and frontend actors participate in the same routing tree
379: 
380: **No frontend changes are needed until Wave 3.** The current HTTP transport continues to work as-is. When the WebSocket bridge ships, `NetworkAdapter` will gain a mode switch to route TX messages over WebSocket instead of HTTP, with automatic fallback. The frontend Actor/Matrix system is already designed for this -- `Socket.js` exists and handles reconnection, heartbeat, and message queuing. The missing piece is the backend-side WebSocket endpoint and the TX serialization bridge between Python and JavaScript actors.

22: 
23: **File:** `core/Component.js`
24: **Tag:** Not registered as a custom element (abstract base class)
25: 
26: Unified base class for all N3TX web components. Merges Actor bridge, Shadow DOM, schema resolution, adaptive display, and stylesheet management into a single class.
27: 
28: ### Class Hierarchy
29: 
30: ```
31: HTMLElement
32:   └── Component              (core/Component.js, ~317 lines)
33:         ├── NTTElement       (components/NTTElement.js — entity lifecycle)
34:         │     └── NTTItem    (components/ntx-item.js — built-in default)
35:         └── ListElement      (components/ListElement.js — collection lifecycle)

40: 
41: ```javascript
42: constructor(defaultValue = {}) {
43:   super();
44:   this.attachShadow({mode: 'open'});
45:   // Actor identity
46:   this.#hash = this.getAttribute('hash') || generateId();

48:   matrix.register(this);

50:   // Entity state
51:   this.#model = this.getAttribute('model') || undefined;
52:   this.#data = defaultValue;
53:   // Stylesheet hook
54:   if (this.styles) { /* creates <link> in shadowRoot */ }

110: ### Adaptive Display Mode
111: 
112: Every component gets space-awareness via ResizeObserver. Sizes use abstract names (`xs`–`xl`) with optional semantic aliases (`pill`, `card`, etc.).
113: 
114: **Sizes:**
115: 
116: | Size | Alias | Default Breakpoint | NTTItem Rendering |
117: |------|-------|--------------------|-------------------|
118: | `xs` | `pill` | 0px+ | Name badge only |
119: | `sm` | `list-item` | 200px+ | Compact row: name + 2–3 key fields |
120: | `md` | `card` | 400px+ | Full card: edit + form + methods |
121: | `lg` | `detail` | 600px+ | Detail view (future: normally-hidden fields) |
122: | `xl` | `page` | 800px+ | Page view (future: full metadata) |
123: | `row` | `row` | n/a | Table row layout for `NTTRow`; not selected by ResizeObserver |
124: 
125: **Auto mode (default):** ResizeObserver measures component width and resolves to the largest matching breakpoint.

192: ## NTTElement
193: 
194: **File:** `components/NTTElement.js`
195: **Tag:** Not registered (abstract base — use `NTTItem` or extend directly)
196: 
197: Single entity base class. Handles the data lifecycle for one entity instance.
198: 
199: ### Constructor
200: 
201: ```javascript
202: constructor() {
203:   super({});  // Default value: single entity object
204: }
205: ```
206: 
207: ### Value Override
208: 
209: ```javascript
210: set value(data) {
211:   super.value = data;
212:   // Auto-renders when schema + data are both available
213:   if (this.schema && this.schema.__name__) {
214:     this.render();
215:   }
216: }
217: ```
218: 
219: ### Message Handlers
220: 
221: | Handler | Trigger | Behavior |
222: |---------|---------|----------|
223: | `UPDATE(data)` | TT watcher notification | Validates `$schema` field, sets value. If schema source changed, sends CONNECT. |
224: | `DESCRIBE(data)` | N3TX instance ATTACH response | Sets `schema = data.proto`, `value = data.data`, renders. Also subscribes to entity signal for live updates — future value changes (e.g., after `pull()`) automatically re-render. |
225: | `READ(data)` | Direct URL fetch response | Looks up DynamicClass from `data-model` attribute, sets schema + value. |
226: 
227: ### Entity Signal Subscription
228: 
229: When `DESCRIBE` is called, the component subscribes to the N3TX entity's signal. This means:
230: - After a method call, the entity's `_response_` handler either applies a structured local update (`{action, _field, id}`), updates same-entity payloads directly, or falls back to `pull()` for ambiguous / child-entity responses. Any entity value change notifies the component via the signal.
231: - The subscription is cleaned up in `disconnectedCallback()` to prevent memory leaks.
232: 
233: ### Save
234: 
235: ```javascript
236: save() {
237:   // Sends UPDATE TX with current value to this.ref
238:   this.send(new TX({ name: 'UPDATE', source: this.addr, target: this.ref, data: this.value }));
239: }
240: ```
