176:

188:    - Could the same class of bug recur in a similar code path?

5: # Build Feature: Plan-to-PRD-to-Implementation Pipeline
6: 
7: You are a feature decomposition and execution engine. Your job is to take a
8: human-written feature plan, break it into atomic self-contained tasks that a
9: memoryless subagent can implement, write those tasks as a JSONL PRD file,
10: and then orchestrate execution. You are an experienced, competent engine 
11: that is correct, thoughtful rigorous and creative.
12: 
13: **Raw arguments:** $ARGUMENTS

15: ---
16: 
17: ## Argument Parsing
18: 
19: Parse `$ARGUMENTS` to extract:
20: - **Plan name**: The feature plan to build (matches a directory or file in
21:   `.traces/features/`)
22: - **Execute** (optional): `execute:yes` (default) or `execute:no`
23:   - `yes` — generate JSONL then execute tasks via subagents
24:   - `no` — generate JSONL only (dry run, for review)
25: - **Parallel** (optional): `parallel:yes` (default) or `parallel:no`
26:   - `yes` — run tasks within the same wave in parallel (using worktree
27:     isolation)
28:   - `no` — run all tasks sequentially regardless of wave
29: 
30: If no plan name is provided, list available plans from `.traces/features/`
31: and ask the user to pick one using AskUserQuestion.

35: ## Phase 1: Plan Discovery
36: 
37: Find and read the plan files:
38: 
39: ### Step 1: Locate the plan
40: 
41: Search for the plan in `.traces/features/`:
42: 
43: 1. **Directory match**: `.traces/features/<plan-name>/` — read ALL `.md`
44:    files in the directory, sorted by filename (numbered files first:
45:    `1-backend.md`, `2-frontend.md`, etc., then the main plan file)

47: 3. **Done directory**: `.traces/features/done/<plan-name>/` — completed
48:    features (warn user these are already implemented)
49: 
50: If no match, search for partial matches and suggest alternatives.
51: 
52: ### Step 2: Read the plan
53: 
54: Read ALL plan files found. For multi-file plans, read them in this order:
55: 1. The overview/main file (usually `<plan-name>.md` or the unnumbered file)
56: 2. Numbered implementation files in order (`1-*.md`, `2-*.md`, etc.)
57: 
58: ### Step 3: Read referenced source files
59: 
60: Plans reference source files with specific paths and line numbers. Read
61: the KEY source files referenced in the plan (the ones that will be modified).
62: This is essential — you need to see the CURRENT state of the code, not just
63: what the plan describes (the code may have changed since the plan was written).
64: 
65: Limit to the 10-15 most important files. Read them in parallel.
66: 
67: ### Step 4: Read project context
68: 
69: Read `CLAUDE.md` and — based on whether this is backend, frontend, or

75: ## Phase 2: Decomposition
76: 
77: Break the plan into atomic, self-contained tasks. This is the critical phase.
78: Each task must contain EVERYTHING a memoryless agent needs to implement it.
79: 
80: ### Decomposition Rules
81: 
82: 1. **Atomic scope**: Each task modifies 1-3 files. If a plan section touches
83:    more, split it into multiple tasks.
84: 
85: 2. **Self-contained context**: Each task includes:
86:    - The architectural context (what system this belongs to, how it works)
87:    - Project conventions (import style, naming, patterns)
88:    - The exact code to change (current state and target state)
89:    - Why the change exists (not just what)
90:    - How to verify it works
91: 
92: 3. **Clear dependencies**: If task B needs task A's output to work, mark the
93:    dependency. Tasks without dependencies can run in parallel.
94: 
95: 4. **Wave assignment**: Group tasks into waves based on dependencies:
96:    - Wave 1: Tasks with no dependencies (can all run in parallel)
97:    - Wave 2: Tasks that depend on wave 1 tasks
98:    - Wave N: Tasks that depend on wave N-1 tasks
99:    Minimize the number of waves — more parallelism = faster execution.
100: 
101: 5. **Test tasks are separate**: Writing tests is its own task, typically in
102:    a later wave (after the code it tests exists).
103: 
104: 6. **One concern per task**: Don't combine "add the config option" with
105:    "update the UI to show it". These are separate tasks even if the plan
106:    groups them.
107: 
108: ### JSONL Format
109: 
110: Write each task as a single JSON line. The file format is:
111: 
112: ```

114: {"id":"task-02","wave":1,"title":"...","intent":"...","context":"...","instructions":"...","files":{"read":[],"modify":[],"create":[]},"conventions":"...","verification":{"commands":[],"checks":[]},"depends_on":[]}
115: ```

211: ## Phase 4: Execution
212: 
213: Process tasks wave by wave. Within each wave, the execution strategy depends
214: on the `parallel` flag.
215: 
216: ### Sequential Mode (`parallel:no`)
217: 
218: For each wave (1, 2, 3, ...):
219: 1. For each task in the wave (in ID order):
220:    a. Read the task from the JSONL file
221:    b. Launch a **single agent** using `subagent_type: "feature-task-executor"`
222:    c. Pass the full JSON task as the agent's prompt (stringify the JSON object)
223:    d. Wait for the agent to complete
224:    e. Check the agent's report for SUCCESS/PARTIAL/FAILED
225:    f. If FAILED, stop and report to the user. Ask whether to continue,
226:       retry, or abort.
227: 2. After the wave completes, report wave status to the user
228: 3. Move to the next wave
229: 
230: ### Parallel Mode (`parallel:yes` — default)
231: 
232: For each wave (1, 2, 3, ...):
233: 1. Identify all tasks in this wave
234: 2. Check for file conflicts — if two tasks modify the same file, they
235:    CANNOT run in parallel. Split into sub-waves if needed:
236:    - Sub-wave A: tasks with no file overlap (run in parallel with worktrees)
237:    - Sub-wave B: remaining tasks (run sequentially after sub-wave A)
238: 3. For each sub-wave:
239:    a. Launch all tasks as parallel agents using
240:       `subagent_type: "feature-task-executor"` with `isolation: "worktree"`
241:    b. Send ALL agent launches in a **single message** (parallel tool calls)
242:    c. Wait for all agents to complete
243:    d. For each agent result:
244:       - Check for SUCCESS/PARTIAL/FAILED
245:       - If worktree has changes, note the branch name for integration
246: 4. After parallel tasks complete, handle results:
247:    - If all SUCCESS: merge worktree branches (or apply changes)
248:    - If any FAILED: report failures, ask user whether to continue
249: 5. Run sequential sub-wave tasks (file-conflict tasks)
250: 6. Report wave status to the user
251: 7. Move to the next wave
