304: 
305: The actor HTTP adapter no longer generates these parent-scoped routes:
306:

321: 
322: If your client called parent-scoped actor routes, migrate to one of these
323: N3TX-native patterns:
324:

326:    - Before: `POST /products/5/comments`
327:    - After: `POST /comments` or `POST /Comment`
328:    - Include the relationship field in the body when the child/link model owns
329:      an explicit FK/ref field, for example `{"product_id": 5, ...}`.
330:

332:    - Define a method such as `Product.comment(...)` with `@expose_route`.
333:    - Call `POST /Product/5/comment` or `POST /products/5/comment`.
334:    - Keep append/toggle/validation behavior inside the model method instead of
335:      encoding it in a generated nested route.
336: 
337: 3. **Use schema-declared relationships plus populate for reads.**
338:    - Define local owned collections as model fields, for example
339:      `comments: list[Comment]`.
340:    - Read the parent with `GET /Product/5?populate=comments&depth=1` when the
341:      UI or caller needs related child data.
342:

344:    - Use model fields, `__access__`, protected fields such as `user_owner`, and
345:      custom methods for ownership semantics.
346:    - Do not rely on a URL parent segment to imply authorization or persistence
347:      behavior.

1: # Universal Context Protocol (UCP) Specification — Draft v0.1
2: 
3: ## Introduction
4: The **Universal Context Protocol (UCP)** is a specification designed to enable seamless and standardized communication between heterogeneous backend systems and user interfaces. UCP aims to provide a machine-inspectable and semantically rich context model for interoperable data exchange, introspection, and presentation.
5: 
6: UCP is inspired by the strengths of GraphQL, JSON Schema, and REST, while simplifying the protocol to support wide adoption across backends with minimal implementation effort.
7: 
8: ---
9: 
10: ## Goals
11: 
12: - 📡 Define a protocol enabling frontends to query and interact with arbitrary backend services.
13: - 🧠 Encode machine-readable schema for all accessible objects.
14: - 🔍 Enable schema discovery, introspection, and contextual documentation.
15: - 🔄 Support dynamic UI rendering from backend types.
16: - 🧩 Be backend-agnostic and compatible with REST, RPC, and WebSocket-style APIs.
17: 
18: ---
19: 
20: ## Architecture Overview
21: 
22: - **Schema Endpoint**: Provides the introspectable type and endpoint structure.
23: - **Context Objects**: Objects provided by the backend, described using UCP Type Schema.
24: - **Operations**: Actions (GET, POST, PUT, DELETE) described declaratively alongside schemas.
25: - **Frontend Resolver**: Client-side interpreter that reads UCP schema and dynamically builds UI/forms.
26: 
27: ---
28: 
29: ## Core Concepts
30: 
31: ### 1. UCP Schema
32: Each backend implements a single schema endpoint, e.g. `/ucp/schema`, returning a full description of types and endpoints:
33: 
34: ```json
35: {
36:   "version": "0.1",
37:   "types": { "User": {...}, "Product": {...} },
38:   "endpoints": [
39:     {
40:       "route": "/users",
41:       "method": "POST",
42:       "input": "User",
43:       "output": "User"
44:     },
45:     {
46:       "route": "/products/list",
47:       "method": "GET",
48:       "output": "Product[]"
49:     }
50:   ]
51: }
52: ```
53: 
54: ### 2. Type Descriptions
55: Each UCP ProtoType contains:
56: 
57: ```json
58: {
59:   "prototype": "<Class Name>",
60:   "description": "A human readable description of the type. It will be used for documentation and LLM parsing purposes.",
61:   "fields": {
62:     "id": { "type": "int", "readOnly": true },
63:     "name": { "type": "string" },
64:     "email": { "type": "string", "format": "email" }
65:   }
66: }
67: ```
68: 
69: ### 3. Instanciated object representation
70: 
71: ### 4. Endpoint Objects
72: Each operation endpoint includes:
73: - `route`: Relative URL
74: - `method`: HTTP verb
75: - `input`: Optional input type (UCP type reference)
76: - `output`: Output type or array
77: 
78: ---
79: 
80: ## Specification Requirements
81: 
82: ### Minimal Backend Support
83: A UCP-compliant server must:
84: - Serve a static or dynamic `/ucp/schema` endpoint that provides the 
85:   server's topology
86: - Serve a static or dynamic `/ucp/<prototype>` endpoint that provides the
87:   prototype for a given type
88: - Provide type metadata for all exposed objects
89: - Provide endpoint metadata for all operations
90: 
91: ### Roadmap features
92: - `examples`, `descriptions`, and `tags` fields for documentation
93: - `permissions`, `validators`, and `hints` for frontend rendering
94: 
95: ---
96: 
97: ## Roadmap
98: 
99: ### v0.1 (Current)
100: - Type and endpoint schema definitions
101: - Static discovery format
102: 
103: ### v0.2
104: - Server metadata (name, description, auth info)
105: - Partial query introspection (field subsets)
106: 
107: ### v1.0
108: - Dynamic resolvers
109: - Standardized error model
110: - WebSocket or subscription support
111: 
112: ---
113: 
114: ## Comparison with GraphQL
115: | Feature                | UCP           | GraphQL        |
116: |------------------------|----------------|----------------|
117: | Introspection         | ✅             | ✅              |
118: | REST compatibility    | ✅             | ❌              |
119: | Type system           | JSON-inspired  | GraphQL Schema |
120: | Transport flexibility | ✅ (HTTP/WS/etc)| Mostly HTTP     |
121: | Frontend dynamic UI   | ✅             | ⚠️ (custom tooling required) |
