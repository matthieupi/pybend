523: 
524: The `schema()` method adds `$schema` (pointing to `{API_URL}/Schema`) and `$id` (pointing to `{API_URL}/{ClassName}`) to the top-level schema dict, and `$id` to each `$defs` entry.
525: 
526: Storable models can be accessed through either the original table-name API or
527: the class-name JSON mirror grammar:
528: 
529: ```text
530: GET  /users/1  -> legacy table-name JSON read
531: GET  /User/1   -> class-name read mirror of the same entity
532: GET  /User/_   -> class-name collection mirror
533: POST /User     -> class-name create mirror
534: PUT  /User/1   -> class-name update mirror
535: ```
536: 
537: Both update route grammars accept narrow patches, matching Python
538: `Model.update(id, patch)`, actor TX updates, and agent update tools. Omitted
539: fields remain unchanged. Supplied values are merged with the current entity and
540: validated through the original model before persistence. See
541: [CRUD Endpoints](API_CRUD_ENDPOINTS.md#update-resource).
542: 
543: Entity payloads keep `$schema` pointing to `/{ClassName}` and now advertise
544: `$id` as `/{ClassName}/{id}`, even when fetched through the legacy table-name
545: route. Literal custom methods may also be mirrored under class-name paths, for
546: example `/User/1/run`; there is no generic method catch-all.
547: 
548: View routes reserve `@` for HTML/component entrypoints, for example
549: `GET /User/@` and frontend hashes such as `#User/@table`; those routes are not
550: JSON data routes.
551: 
552: Custom method responses, including auth methods such as `/users/login` and
553: `/users/register`, may be returned either as the method payload directly or under
554: `data` when response debugging/enveloping is enabled. Browser test helpers should
555: read auth tokens with `body.token ?? body.data?.token` rather than assuming only
556: one envelope shape.
557: 
558: This is useful for:
559: - Dynamic form generation
560: - Client-side validation
561: - Auto-generating TypeScript types

94: ## Models
95: 
96: ### ProtoModel
97: 
98: Base class for all N3TX models. Provides schema generation, validation, and optional storage.
99: 
100: **Module**: `models.proto_model`
101: 
102: #### Config
103: 
104: ProtoModel sets `extra='allow'` in its Pydantic Config. This allows extra fields like `$schema` and `$id` to be included in serialized output without being rejected by FastAPI's response model validation.
105: 
106: #### Class Variables
107: 
108: ```python
109: class MyModel(ProtoModel):
110:     __storable__: ClassVar[bool] = True        # Enable CRUD operations
111:     __tablename__: ClassVar[str] = 'my_models' # Database table name
112: ```
113: 
114: #### Class Methods
115: 
116: ##### `schema() -> Dict[str, Any]`
117: 
118: Returns the complete JSON schema for the model via the composable schema pipeline (`proto_schema.run_pipeline(cls)`). The pipeline consists of 8 stages: `base`, `strip_hidden`, `methods`, `agent`, `defs`, `access`, `ui`, `metadata`. Extensions can insert additional stages via `@schema_extension`.
119: 
120: The schema output includes:
121: - `$schema` at the top level, pointing to `{API_URL}/Schema`
122: - `$id` at the top level, pointing to `{API_URL}/{ClassName}`
123: - `$id` on each entry in `$defs`, pointing to `{API_URL}/{DefClassName}`
124: 
125: The schema endpoint is `GET /{ClassName}`. For storable models, N3TX also
126: registers class-name JSON mirrors for collection, create, read, update, delete,
127: and literal custom methods. Those mirrors return the same entity payloads as
128: the table-name routes and advertise entity `$id` values using
129: `/{ClassName}/{id}`.

204: 1. `base` -- plain Pydantic `model_dump()`
205: 2. `relationships` -- enriches hydrated `T` and `list[T]` children

592: Generic type-safe wrapper for foreign key relationships.
593: 
594: **Module**: `utils.typer`
595: 
596: #### Constructor
597: 
598: ```python
599: Ref[T](value: Optional[Any] = None)
600: ```
601: 
602: **Parameters**:
603: - `value`: Can be:
604:   - `BaseModel` instance: Extracts ID
605:   - `int`: Stores directly
606:   - `dict`: Extracts 'id' key
607: 
608: **Example**:
609: ```python
610: from utils.typer import Ref
611: 
612: class Comment(ProtoModel):
613:     user: Ref[User]  # Type-safe foreign key
614: ```
615: 
616: #### Methods
617: 
618: ##### `__int__() -> int`
619: 
620: Returns the foreign key ID.
621: 
622: **Example**:
623: ```python
624: comment = Comment(...)
625: user_id = int(comment.user)  # Extracts ID
626: ```
627: 
628: ##### `model_dump() -> int`
629: 
630: Serializes to integer for storage.
631: 
632: #### Schema Generation
633: 
634: `__get_pydantic_json_schema__` outputs `$schema` and `$id` (instead of the old `__url__` and `__type__` fields) when generating the JSON schema for foreign key references:
635: 
636: ```python
637: # Model definition
638: class Comment(ProtoModel):
639:     user: Ref[User]

643:   "type": "object",
644:   "properties": {
645:     "user": {
646:       "type": "$ref",

648:     }
649:   }
