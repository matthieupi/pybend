261: ## Frontend Split Rationale
262: 
263: The backend split axis (core/actors/agents) doesn't map to the frontend. Analysis of the JS import graph:
264: 
265: - **Component.js** imports Actor, Matrix, AND TX — it's the base for every web component
266: - **NTT.js** extends Actor and uses Matrix — it's the entity registry
267: - Every `ntx-*` component transitively depends on all three "actor" files
268: 
269: The frontend split axis is **runtime vs. visual**:
270: - **n3tx-core**: Non-visual runtime — messaging, entity system, abstract component bridge, transport, utils
271: - **n3tx-ui**: Visual layer — registered custom elements, visual base classes, form generator, widgets, themes
272: - **n3tx-agents**: Agent-specific UI — `ntx-chat.js` only
273: 
274: No circular dependencies:
275: ```
276: core ← ui      (ui imports from core, never reverse)
277: core ← agents  (agents imports from core, never reverse)
278: ui and agents are independent of each other
279: ```

281: ## Static File Serving (Multi-Package)
282: 
283: Three packages bundle `static/` directories (n3tx-core, n3tx-ui, n3tx-agents). At runtime, `N3TXApp` discovers and merges them into a single URL namespace.

286: 1. App-specific static dirs (from `create_app(static_dir=...)`)
287: 2. n3tx-agents static (if installed) — `ntx-chat.js`
288: 3. n3tx-ui static (if installed) — all components, widgets, themes, default HTML

293: ## Schema as Universal Contract
294: 
295: The JSON Schema returned by `GET /{ClassName}` is the **single contract between backend and frontend**. It is not just a type description — it is the complete specification of how an entity behaves, renders, and is controlled.
296: 
297: For full schema anatomy details, see `/workspace/docs/CORE.md`.
298: 
299: ### How Each Schema Section Is Consumed
300: 
301: **Frontend reads schema once, adapts everything at runtime:**
302: 
303: | Schema section | Frontend consumer | What it controls |
304: |---------------|------------------|-----------------|
305: | `properties` | `prototype()` in NTT.js | Creates typed getters/setters on DynamicClass |
306: | `properties[field].type` | `form.js` → `getInput()` | Chooses input type (text, number, checkbox, ...) |
307: | `properties[field].x-ref` | widget registry → `ReferenceWidget` | Marks an HTTP(S) URL string as a typed model pointer without overloading JSON Schema `$ref` |
308: | `properties[field].ui.widget` | `form.js` → `getInput()` | Specialized rendering (currency prefix, textarea) |
309: | `properties[field].ui.display` | `form.js` → field filtering | Hides internal fields |
310: | `properties[field].ui.protected` | `form.js` → field filtering | Hides backend-owned fields in edit mode |
311: | `properties[field].ui.placeholder` | `form.js` → input attrs | Sets placeholder text on inputs |
312: | `properties[field].access` | `Permissions.js` → `canView()` | Field-level visibility per user role |
313: | `ui.field_order` | `form.js` → `getForm()` | Controls field rendering sequence |
314: | `ui.groups` | `form.js` → `renderGroupedFields()` | Wraps fields in `<fieldset>` groups |
315: | `ui.description` | `NTTList.render()` | Optional collection intro text under the header title |
316: | `ui.create_label` | `NTTList.render()` | Optional labeled collection create button |
317: | `ui.icon` | `ntx-icon` + icon resolver | Shared icon rendering for model shells and method actions |
318: | `ui.renderer.*` | `ntx-router.js` → `#resolveTag()` | Chooses component tag for navigation views |
319: | `access` | `Permissions.js` → `canAction(access, action, resource)` | Shows/hides edit/delete buttons with resource-aware OWNER evaluation |
320: | `methods` | `prototype()` + `<ntx-method>` / `<ntx-stream>` | Creates callable methods + renders action buttons |
321: | `$defs` | `NTT.SCHEMA()` | Registers nested DynamicClasses |
322: | `$id` / `$schema` | DynamicClass value getter | Injected into every entity instance for self-description |

343: ### Schema Propagation Lifecycle
344: 
345: ```
346: 1. Model Definition (Python)
347:    Product(ProtoModel) with fields, __ui__, __access__, @expose_route
348:                     │
349: 2. Schema Generation (Backend, on GET /Product)
350:    ProtoModel.schema() → proto_schema pipeline (base → strip_hidden → methods → defs → access → widget → ui → metadata)
351:                     │
352: 3. Network Transport
353:    HTTP GET /Product → JSON response
354:                     │
355: 4. Schema Bootstrap (Frontend)
356:    NTT.SCHEMA(data) → prototype(addr, schema, href) → DynamicClass
357:    │  Creates typed class with getters, setters, methods from schema
358:    │  Registers nested $defs as additional DynamicClasses
359:                     │
360: 5. Component Rendering (Frontend)
361:    NTTItem.DESCRIBE() receives { proto: schema, data: values }
362:    │  form.js reads schema.properties → builds form HTML
363:    │  Permissions.js reads schema.access → shows/hides controls
364:    │  ntx-method reads schema.methods → renders action buttons
365:    │  ntx-router reads schema.ui.renderer → resolves navigation targets
366:                     │
367: 6. Entity Responses (Backend, on GET /products)
368:    model_response() runs dump pipeline → injects $schema + $id into each record
369:    │  Frontend DynamicClass value getter preserves these for self-description
370:     │  Owned T/list[T] fields retain hydrated child objects with flat $id values
371: ```

400: ### Hash Route Grammar and View Resolution
401: 
402: The frontend router uses an explicit `@` segment for model view routes. This
403: keeps presentation separate from method/action routing while preserving legacy
404: hash links.
405: 
406: | Route | Meaning | Mount attrs |
407: |---|---|---|
408: | `#Product` | Legacy/default collection route | `{ model: 'Product' }` |
409: | `#Product?view=table` | Legacy query-selected collection view | `{ model: 'Product' }` plus query params except `view` |
410: | `#Product/@` | Collection default view | `{ model: 'Product' }` |
411: | `#Product/@table` | Collection named view | `{ model: 'Product' }` |
412: | `#Product/1` | Legacy/default member detail route | `{ ref: 'Product/1', display: 'lg' }` |
413: | `#Product/1/@` | Member default view | `{ ref: 'Product/1', display: 'lg' }` |
414: | `#Product/1/@chat` | Member named view | `{ ref: 'Product/1', display: 'lg' }` |
415: | `#Product/1/run` | Method/action route | `{ ref: 'Product/1', method: 'run', display: 'lg' }` |
416: | `#Product/1/@run` | View named `run`, not a method | no `method` attr |
417: | `#Product/1/Comment/2` | Legacy nested navigation alias | `{ data-model: 'Comment', ref: 'Comment/2', display: 'lg' }` |
418: | `#Product/1/Comment/2/@item` | Legacy nested member-view alias | `{ data-model: 'Comment', ref: 'Comment/2', display: 'lg' }` |
419: | `#Product/1/Comment/2/like` | Legacy nested action alias | `{ data-model: 'Comment', ref: 'Comment/2', method: 'like', display: 'lg' }` |
420: | `#@profile` | App-level route | mounts `<ntx-profile>` |
421: 
422: `Router.parseRoute()` normalizes leading/trailing slashes and rejects invalid
423: model view tokens instead of silently treating them as IDs or actions. Valid view
424: tokens match `[A-Za-z0-9][A-Za-z0-9_-]*`. `Router.resolveRoute()` validates
425: resolved component tags before returning a mount instruction.
426: 
427: Semantic view names resolve through the schema first:
428: 
429: ```text
430: Collection default: renderer.page -> renderer.list -> ntx-list
431: Collection named:   renderer[view] -> known fallback (list/table) -> invalid
432: Member default:     renderer.detail -> renderer.item -> ntx-item
433: Member named:       renderer[view] -> known fallback (item/detail/chat) -> invalid
434: ```
435: 
436: Path-based `@view` selection takes precedence over query `view`. User-facing
437: query parameters pass through to the mounted component, but internal route
438: controls such as `view` are filtered from attrs.
439: 
440: Legacy nested class-name hash routes remain navigation aliases:
441: 
442: ```text
443: #Product/1/Comment/2
444: ```
445: 
446: They do not define entity or transport identity. Resolution discards the parent
447: segments and mounts the child through its canonical `Comment/2` NTT address.
448: Backend responses remain authoritative through the child's flat `$id`, such as
449: `/Comment/2`; the frontend never synthesizes a parent-scoped child `$id`.
450: 
451: The parser shape for nested details is:
452: 
453: ```js
454: {
455:   type: 'nested-detail',
456:   parentModel: 'Product',
457:   parentId: '1',
458:   model: 'Comment',
459:   id: '2',
460:   params: {}
461: }
462: ```
463: 
464: Resolution mounts the child under its semantic cache identity:
465: 
466: ```text
467: mounted attrs:   data-model="Comment" ref="Comment/2"
468: NTT cache key:   Comment/2
469: transport href: <API_URL>/Comment/2
470: ```
471: 
472: Nested view and action routes preserve the existing `@` boundary:
473: 
474: ```text
475: Product/1/Comment/2/like   -> nested action, `method="like"`
476: Product/1/Comment/2/@like  -> nested view, no `method` attr
477: ```

487: ### Streaming Transport
488: 
489: The frontend transport layer supports streaming for long-running operations. See `packages/n3tx-ui/docs/components.md` for the `<ntx-stream>` component.
490: 
491: #### HTTP.stream()
492: 
493: `HTTP.stream(url, data, onChunk, onDone, onError)` — SSE client using Fetch API with `ReadableStream`. Parses `event: chunk|done|error` and `data: {json}` lines. Returns `{ cancel: Function }` for AbortController cancellation.
494: 
495: A `_done` guard prevents double `onDone` callbacks when SSE `event: done` is followed by ReadableStream closure.
496: 
497: ```javascript
498: const handle = HTTP.stream('/products/1/generate', { prompt: 'hello' },
499:     (chunk) => console.log('Chunk:', chunk),
500:     (data)  => console.log('Done:', data),
501:     (err)   => console.error('Error:', err),
502: );
503: handle.cancel();  // Cancel mid-stream
504: ```
505: 
506: #### Socket.registerStream()
507: 
508: `socket.registerStream(reqId, onChunk, onDone, onError)` — registers stream handlers for correlated WS messages. Messages with `meta.stream` and matching `meta.req` are dispatched to the registered handler.
509: 
510: #### NetworkAdapter.sendStream()
511: 
512: `adapter.sendStream(event, onChunk, onDone, onError)` — unified streaming API. Uses WebSocket if connected, falls back to HTTP SSE.
513: 
514: #### `<ntx-stream>` Component
515: 
516: Extends `NTTMethod`. For methods with `schema.methods[m].stream === true`. Renders progressive output with blinking cursor, cancels in-flight streams on disconnect.
517: 
518: ```html
519: <ntx-stream model="Product" uuid="1" method="generate" label="Generate"></ntx-stream>
520: ```

522: ### NTTStreamAgent (Agent Streaming)
523: 
524: **File**: `packages/n3tx-agents/src/n3tx_agents/static/components/ntx-stream-agent.js`
525: 
526: Extends `NTTStream` with rich agent output rendering — typed entries (thinking, tool calls, text), markdown rendering, and tool result cards. All agent-style streaming components extend `NTTStreamAgent` (or `NTTStream` directly for simpler cases):
527: 
528: ```javascript
529: import { NTTStreamAgent } from './ntx-stream-agent.js';
530: 
531: class MyComponent extends NTTStreamAgent {
532:     // UPPERCASE = TX inbox handlers (actor convention)
533:     TEXT(data, meta)       { /* data.text */ }
534:     TOOL_CALL(data, meta)  { /* data.tool, data.args, data.call_id */ }
535:     DONE(data, meta)       { /* data.answer, data.usage */ }
536: 
537:     // Lifecycle hooks
538:     STREAM_END(data)       { /* stream completed */ }
539:     STREAM_ERROR(err)      { /* error */ }
540: }
541: ```
542: 
543: **Component hierarchy:**
544: 
545: ```
546: Component → NTTMethod → NTTStream → NTTStreamAgent → (app subclasses)
547: ```
548: 
549: **Lifecycle hooks:**
550: 
551: | Method | When | Purpose |
552: |--------|------|---------|
553: | `prerender()` | `connectedCallback()`, before schema | Structural DOM (shell, layout). Never wiped by render(). |
554: | `render()` | After schema arrives | Additive updates (title, etc.). Must not wipe prerender() output. |
555: | `callMethod()` | User triggers execution | Starts stream. Generates `#streamReqId` correlation ID. |
556: | `cancel()` | Cleanup / user action | Sets `#cancelled` flag, sends `STREAM_CANCEL` TX, calls `STREAM_END`. |
557: | `disconnectedCallback()` | Element removed | Auto-calls `cancel()` for cleanup. |
558: 
559: **Dispatch flow:**
560: 
561: 1. `callMethod()` sends TX with `meta: {stream: true, req: reqId}` via Actor system
562: 2. Backend sends stream chunks as TX messages
563: 3. `NTTStream.STREAM()` handler receives chunks, skips if `#cancelled`
564: 4. Dispatches to UPPERCASE handlers: `THINKING()`, `TOOL_CALL()`, `TEXT()`, `DONE()`, `STREAM_END()`, `STREAM_ERROR()`
565: 
566: **UPPERCASE convention**: All methods that handle TX messages are UPPERCASE. lowercase/camelCase = internal component logic. This mirrors the backend actor handler pattern.
567: 
568: **Concrete components extending NTTStream:**
569: - `<ntx-agent-live>` — Real-time agent activity log with structured event rendering
570: - `<ntx-chat>` — Floating chat panel for conversational agent interaction
571: 
572: Both extend `NTTStream` directly, use `prerender()` for structural UI, and auto-cancel streams in `disconnectedCallback()`.

574: ### Schema-Declared Stream Events
575: 
576: Streaming methods can declare their event vocabulary via `events=` on `@expose_route` (backend). The schema pipeline serializes these into `schema.methods[m].events`:
577: 
578: ```json
579: {
580:   "methods": {
581:     "agentic_stream": {
582:       "stream": true,
583:       "events": {
584:         "text": {"type": "object", "properties": {"text": {"type": "string"}}},
585:         "tool_call": {"type": "object", "properties": {"tool": {...}, "args": {...}}},
586:         "done": {"type": "object", "properties": {"answer": {...}, "usage": {...}}}
587:       }
588:     }
589:   }
590: }
591: ```
592: 
593: Frontend components can read `events` to discover available chunk types and validate their handler coverage.
