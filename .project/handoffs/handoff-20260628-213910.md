# Handoff — N3TX Actor ERROR Catch Semantics for RemoteMatrix Failures

Generated: 2026-06-28 21:39:10 UTC
Session focus: Prepare a framework-team handoff for evaluating and implementing actor-level `ERROR` catch semantics that stop recursive TX forwarding while preserving observable Task/Scene failure state.

## ✅ Executive Snapshot

- The user reported an infinite loop after `GENERATE()` → `STOP()` → `STOP()` again → `GENERATE()` again in a Gaussian Splat Capture Portal app built on N3TX.
- The loop logs repeatedly show `Remote target requires an id for ERROR: n3tx://compute/Process`, followed by `Error in ERROR: maximum recursion depth exceeded`.
- The app intentionally defines a domain `Task.ERROR(...)` method to behave like actor-level `try/catch`; the user wants to preserve that concept, not remove it.
- Recommended framework-level fix: **incoming `ERROR` TXs may be handled by actor `ERROR` handlers, but the actor system must never reply to an `ERROR` TX**. `ERROR` handling should be terminal/one-way.
- No production code was changed in this session. No tests were run beyond read-only code exploration; this document is intended for the upstream N3TX team, which may not have access to the app repo.

## 🧵 Conversation Context

1. The user first reported a production/runtime crash from clicking **Generate** in the frontend Scene detail view. The logs showed recursive remote error forwarding:

   ```text
   Remote target requires an id for ERROR: n3tx://compute/Process
   app-1 | ERROR: n3tx.actors: [scenes_tasks] Error in ERROR: maximum recursion depth exceeded
   app-1 | WARNING: n3tx.network.remote: RemoteMatrix request failed for n3tx://compute/Process: Remote target requires an id for ERROR: n3tx://compute/Process
   ... repeats ...
   ```

2. Initial analysis identified two interacting issues:
   - Remote transport failure was being delivered as a protocol `ERROR` TX.
   - The app has an exposed `Task.ERROR(...)` method, so ActorModel dispatch treated the protocol `ERROR` as a normal domain method and replied to it.

3. The user corrected the reproduction path. The bug happens specifically after:

   ```text
   1. GENERATE()
   2. STOP() -> marks scene as stopping
   3. click STOP again -> marks scene as stopped
   4. GENERATE() again -> infinite loop
   ```

4. The user split the desired behavior into two bugs:
   - **A)** `ERROR` should not recurse. It should propagate to Scene/Task where it becomes visible in status/error state and frontend observability.
   - **B)** `GENERATE()` should not lead to an unhandled error.

5. An initial proposed fix suggested renaming/removing `Task.ERROR` and using explicit `Task.START()` request/response handling. The user pushed back: the whole point of `ERROR` is to catch actor-level failures like a distributed `try/catch`.

6. The resulting agreed direction is simpler and framework-centered:
   - Preserve `ERROR` methods as actor-level catch handlers.
   - Enforce a framework invariant: **handling an incoming `ERROR` is one-way; never reply to it**.
   - This likely solves the crash/loop and may be sufficient for eventual observability without explicitly changing `GENERATE()`.
   - Synchronous `GENERATE()` failure return remains a separate product/semantics decision if immediate failure reporting is required.

## 🗺️ Current Architecture / Flow

```text
browser Scene detail
  -> POST /scenes/{id}/generate
  -> Scene.GENERATE()
  -> Scene._start_task(Task)
  -> TX START target=tasks/{task_id}
  -> Task.START()
  -> TX START target=n3tx://compute/Process      # class-level remote start intent
  -> Matrix adapter fallback
  -> RemoteMatrix
  -> remote compute Process.START or transport failure
  -> ERROR TX back to source task on failure
  -> Task.ERROR(...) catch handler
  -> Task/Scene state should expose failure to frontend refresh
```

- `Task.START()` submits a class-level remote compute start intent to `n3tx://compute/Process` because the app does not know the eventual Process id yet.
- `RemoteMatrix` supports id-less class-level method dispatch only when it can resolve schema method routes; legacy `_url_for()` still requires an id.
- The failure observed is specifically for a protocol `ERROR` response whose `source` is the id-less remote class actor `n3tx://compute/Process`.
- The app frontend already refreshes Scene and Tasks after method calls; backend state propagation is enough for observability if the loop is stopped.

- `TX.error(...)` creates a message with:

  ```python
  name='ERROR'
  source=self.target
  target=self.source
  data={'message': message, 'code': code}
  meta={**self.meta, 'req': self.uuid, 'error': True}
  ```

- `TX.is_error` is true when:

  ```python
  return self.name == 'ERROR' or self.meta.get('error', False)
  ```

- Base `Actor.handler()` already drops unhandled error/response TXs, but only when no handler is found:

  ```python
  if tx.is_error or tx.name.endswith('_RESPONSE'):
      logger.debug(...)
      return
  ```

- `ActorModel.handler()` has a similar unhandled drop guard, but if an `ERROR` method exists and returns normally, the generic response dispatch still sends a reply.

- `RemoteMatrix.send()` catches request failures and sends `tx.error(...)` to its parent Matrix:

  ```python
  except Exception as exc:
      logger.warning("RemoteMatrix request failed for %s: %s", tx.target, exc)
      response = tx.error(str(exc), code=502)
  await parent.inbox(response)
  ```

### Known to fail

- In the app runtime, after `GENERATE()` → `STOP()` → `STOP()` → `GENERATE()`, `RemoteMatrix` repeatedly logs:

## 💻 Implementation Sketch for N3TX Team

### Framework invariant

```text
Incoming tx.is_error
  -> if target actor has ERROR handler: invoke it for side effects
  -> ignore returned value
  -> if handler raises: log and return
  -> never send tx.reply(), tx.error(), tx.exception(), or ERROR_RESPONSE
```

### Likely patch locations

1. `packages/n3tx-actors/src/n3tx_actors/actor.py`
2. `packages/n3tx-actors/src/n3tx_actors/models/actor_model.py`

### Pseudo-diff: base Actor

```python
async def handler(target, tx: TX) -> None:
    method = getattr(target, tx.name, None)
    if method and callable(method):
        try:
            result = await method(tx.data, tx) if asyncio.iscoroutinefunction(method) else method(tx.data, tx)
        except Exception as e:
            logger.error(f"[{target.addr}] Error in {tx.name}: {e}")
            if tx.is_error:
                return
            await target.send(tx.exception(e))
            return

        if tx.is_error:
            return

        # existing normal response handling
```

### Pseudo-diff: ActorModel

Apply equivalent logic in the custom/exposed method path after method invocation and after coroutine resolution, before response dispatch:

```python
try:
    ... invoke exposed or regular method ...
except Exception as e:
    logger.error(f"[{target.addr}] Error in {tx.name}: {e}")
    if tx.is_error:
        return
    await target.send(tx.exception(e))
    return

if asyncio.iscoroutine(result):
    result = await result

if tx.is_error:
    return

# existing streaming / TX / dict / BaseModel / str response handling
```

### Important nuance

Do not only guard the “unhandled” branch. The bug happens specifically because an `ERROR` handler **is** found and returns successfully.
